# 14 - 设计缺陷深度分析

> 本文档从架构决策、系统复杂度、生产就绪度三个维度，指出设计中的**结构性问题**。
> 不是文档缺陷，而是**系统设计本身的不足**。

---

## 14.1 核心架构的缺陷

### 缺陷 1：置信度系统的信息丢失（严重性：⭐⭐⭐）

#### 问题描述

代码打分的前提是：**质检 Agent 输出的证据清单必须完整**。但质检 Agent 本身也是 LLM，有以下问题：

1. **质检 Agent 本身不稳定**
   - 质检漏判：步骤顺序确实有冲突，但质检 Agent 没发现 → `temporal` 维度虚高
   - 质检误判：不存在的冲突被报告 → 置信度虚低，进不必要的人工复核
   - 质检 Agent 的准确率 SLA (12.6) 定为 90%，但**无法验证**

2. **证据清单的可信度链条太长**
   ```
   材料 Agent → removed_spans → Scorer.completeness ✓
   步骤 Agent → step_conflicts (质检输出) → Scorer.temporal ⚠️（依赖质检）
   工具 Agent → evidence → Scorer.grounding ⚠️（依赖 LLM 输出的 evidence）
   ```
   
3. **反馈循环缺失**
   - 人工复核员发现"置信度虚高"时，无法回流到质检 Agent 重新训练
   - 12.6.2 的"补偿手段"都是**事后发现**，不是**事前预防**

#### 根本原因

设计时**过度信任代码打分**，认为只要质检 Agent 给了证据清单，代码就能准确算分。但：
- LLM 的质检不稳定性根本无法消除
- 没有"质检的质检"（meta-check）机制

#### 风险场景

**场景**：DeepSeek 在某个月表现变差（版本更新、API 变化等）
```
Day 1: 质检 Agent 准确率从 90% 降到 70%
Day 2-7: 大量低质量卡片以 high confidence 直接入库
Day 8: 才在复核队列里发现问题
Day 15: 用户反馈已产生 N 张垃圾卡片
```

**现有防护**：无。12.6.2 的"定期审计"是月度的，太晚了。

#### 改进建议

**方案 A：双质检**（成本 +30%）
```go
// 新增"终检 Agent"，独立质检
// 两个质检的结果对比，不一致时强制进人工复核
terminCheckResult := runTerminalCheckAgent(card)
qcResult := runQualityAgent(card)

if terminCheckResult.ConflictCount != qcResult.ConflictCount {
    // 两个质检打架 → 不能信任代码算分 → 进人工复核
    card.ReviewStatus = "pending_review"
    card.QualityFlags.Append("qc_conflict_detected")
}
```

**方案 B：质检 Agent 预热阶段**（推荐）
```
系统启动时：
1. 用已知答案的 100 条样本测质检 Agent
2. 计算实际 recall / precision
3. 若不达 90% → 报警，不启动应用
4. 若达到 → 记录基准值，后续按周抽检对比

if actualRecall < 0.90 {
    // 不启动，或启动但所有卡片都进人工复核
    card.QualityFlags.Append("qc_accuracy_below_threshold")
}
```

**方案 C：引入专家评分**（最保险但成本高）
```
每周随机抽 50 张 high confidence 卡片
交给数据标注员进行"盲测"评分
与代码算分对比，看一致性
若 N 周内一致性 < 80% → 触发 Prompt 重新训练
```

### 缺陷 2：并行编排中"材料/工具/步骤"的语义不对齐（严重性：⭐⭐⭐⭐）

#### 问题描述

12.1.2 强调"风险 Agent 仅读 `cleaned_text`，不读 `steps_json`"以保证四路并行。但这产生了一个**逻辑矛盾**：

```
步骤 Agent 的输出 → steps[].uses = ["牛皮纸", "美工刀"]
    (原文写法，未做归一化)

质检 Agent 要验证：
  "steps[0].uses 里的'牛皮纸'是否与 materials[] 里的某项对应？"
  
但质检 Agent 读不到 materials[] 的具体值！
只读 raw_text + card JSON → 材料名在 raw_text 里 vs 在 card JSON 里
→ 两套名称，容易不对齐
```

#### 具体场景

```json
// 原文提到
"准备两张牛皮纸和美工刀..."

// 材料 Agent 解析为
materials[0]: { name: "牛皮纸", spec: "A4 120g" }

// 步骤 Agent 解析为（独立读原文）
steps[0]: { uses: ["纸张"] }  // 用了不同的表述！

// 质检 Agent 验证时
"步骤提到'纸张'，但材料清单里没有'纸张'，只有'牛皮纸'"
→ 标记 grounding 问题
→ 置信度降低
→ 进人工复核
```

**这是**质检 Agent**的误判，不是真的 grounding 问题**，但代码无法区分。

#### 根本原因

四路并行的前提是"**互不依赖**"，但实际上它们在**语义层面高度耦合**：
- 步骤引用的材料/工具必须与材料/工具清单对应
- 但各路都是独立调用 LLM，无法保证对齐
- 后期由质检 Agent 校验，但质检本身也不稳定

#### 风险

**置信度系统变成了"LLM 一致性检查"而非"卡片质量检查"**：
- 低置信卡片可能是因为 4 个 Agent 的表述不一致，不是卡片质量差
- 用户看到的 `quality_flags: ["ungrounded:砂纸"]` 其实是"Agent 语言不一致"，不是真实的信息丢失

#### 改进建议

**方案 A：材料/工具 Agent 在并行前先运行** ⚠️（破坏并行）
```
清洗 → [材料/工具（序列）] → [步骤/风险（并行，依赖材料/工具结果）] → 质检
```
这样步骤 Agent 可以在 prompt 里注入材料清单，让 `uses` 自动对齐。

代价：单条耗时从 15s → 20s，P5 吞吐 5300 → 3975 条/天。

**方案 B：归一化层做映射**（推荐）
```go
// 步骤 Agent 输出后，在编排器里做自动映射
steps := runStepAgent(cleanedText)

materials := getCardMaterials()  // 已有材料清单

for step := range steps {
    for use := range step.Uses {
        // 用同义词表 + fuzzy match 与材料清单对齐
        normalized := normalizeName(use)
        for mat := range materials {
            if isSameMaterial(normalized, mat.NameNorm) {
                step.Uses[i] = mat.Name  // 改成规范名称
            }
        }
    }
}
```

这样：
- 不破坏并行
- `steps.uses` 与 `materials` 名称对齐
- 质检 Agent 不会误判 grounding

**方案 C：质检时明确区分两类问题**
```go
// 质检 Agent 的输出加一列：问题类型
type QCIssue struct {
    Type string  // "semantic_drift" / "real_grounding_issue"
    ...
}

// "semantic_drift"：步骤说"纸张"但材料说"牛皮纸"，是表述不一致
// "real_grounding_issue"：材料说有"砂纸"但步骤没提及，是遗漏

// 代码打分时，只有 real_grounding_issue 才扣 grounding 分
```

### 缺陷 3：卡片版本化设计的歧义（严重性：⭐⭐⭐）

#### 问题描述

3.4.3 和 3.4.6 说明了卡片版本化：
```
教程 1 的卡片版本：v1 (is_current=0) / v2 (is_current=1) / v3 (is_current=1) ❌
```

问题1：**`is_current` 的唯一性保证有漏洞**

生成列 + 唯一索引的方案：
```sql
current_tutorial_id = IF(is_current=1, tutorial_id, NULL)
UNIQUE KEY uk_current_card (current_tutorial_id)
```

看起来完美，但有**竞态条件**：

```
事务 A：重跑教程 1
  - 查 SELECT ... FOR UPDATE 得到旧版本 v1
  - 计算新版本 v2
  
事务 B：同时也在重跑教程 1
  - 查 SELECT ... FOR UPDATE 得到旧版本 v1
  - 计算新版本 v2
  
两个事务同时更新 is_current：
事务 A: UPDATE cards SET is_current=0 WHERE tutorial_id=1 AND is_current=1
事务 B: UPDATE cards SET is_current=0 WHERE tutorial_id=1 AND is_current=1
    → 都成功（WHERE 条件对两个事务都成立）

事务 A: INSERT INTO cards (tutorial_id, card_version, is_current=1) VALUES (1, 2, 1)
事务 B: INSERT INTO cards (tutorial_id, card_version, is_current=1) VALUES (1, 2, 1)
    → 冲突！都要插入 (tutorial_id=1, is_current=1)
    → 一个成功，一个报 Duplicate key error
    → 重试...
    → 最坏情况：整个任务失败
```

问题 2：**重跑后的结果对比无法进行**

假设教程 1 原来是 v1（生成的卡片质量一般）。重跑后生成 v2。

用户想对比 v1 vs v2 看改进了没有，但：
- v1 的 `is_current=0` 被设置时，v1 对应的 review_logs 也不清楚要不要保留
- 前端无法显示"这是旧版本，对应的卡片修改历史"

问题 3：**软删与版本化的交互不明**

教程集删除 → 教程级联软删 → 卡片级联软删。但：
```
卡片 v1 (is_current=0, deleted_at=NULL)
卡片 v2 (is_current=1, deleted_at=NULL)

→ 删除教程集
→ is_current 从 1 变 0，deleted_at 变 now()

卡片 v1 (is_current=0, deleted_at=now())
卡片 v2 (is_current=0, deleted_at=now())

→ 恢复教程集（7天内）
→ 需要恢复哪个版本？v1 还是 v2？

如果恢复时直接反转 deleted_at=NULL，那么 v1 和 v2 都活了
但谁应该是 is_current=1？
```

#### 改进建议

**方案 A：用分布式锁保证重跑互斥**
```go
// 重跑前必须加锁
lock := redis.Set("tutorial:rerun:"+tutorialID, 1, EX 30)
if !lock {
    return errors.New("教程正在重跑中，请稍后")
}
defer redis.Del("tutorial:rerun:"+tutorialID)

// 这样同一个教程只能同时有一个重跑任务
```

**方案 B：明确版本恢复策略**
```sql
-- 恢复教程集时
UPDATE cards SET deleted_at=NULL 
WHERE tutorial_id IN (
    SELECT id FROM tutorials WHERE set_id = ? AND deleted_at IS NOT NULL
)
AND (is_current=1 OR card_version = (
    SELECT MAX(card_version) FROM cards c2 
    WHERE c2.tutorial_id = cards.tutorial_id
))

-- 只恢复最新版本（is_current=1）
```

**方案 C：版本对比页面**
```go
// GET /cards/{id}/versions
// 返回该教程所有版本的卡片，支持对比视图
type VersionsResponse struct {
    Current   *Card   // is_current=1
    History   []*Card // is_current=0
    Changes   map[string]interface{} // v1 -> v2 的字段差异
}
```

## 14.2 异步链路的脆弱性

### 缺陷 4：Outbox 模式的重投超时问题（严重性：⭐⭐⭐）

#### 问题描述

3.2 和 5.3 的 outbox 设计：
```
写库 + 写 outbox → 后台协程投 MQ → 消费成功 ACK → 标 confirmed
若投递失败 → outbox 表持续积压 → 定期重投
```

缺陷：**没有说重投的终止条件**。

```sql
-- outbox 表持续积压的场景：
-- RabbitMQ 彻底宕掉，或消费者全挂

-- 理想情况：自动清理
-- 实际情况：行持续增长

-- 假设：100 个消费者，每个消费 100 条/小时
-- 日处理 5300 条 ÷ 24 = 221 条/小时 ÷ 4 消费者 ≈ 55 条/消费者/小时

-- 若消费者全挂（LLM API 熔断 60s），
-- outbox 表在 60s 内积压 221 条
-- 恢复后需要 1-2 小时才能清空

-- 若是 RabbitMQ 故障（4 小时恢复），
-- outbox 积压 ~900 条
```

更严重的是：**没有提及 outbox 表的监控告警**。

#### 风险

```
Day 1 14:00 - RabbitMQ 故障，消费停止
Day 1 14:05 - outbox 积压 50 条（无人发现）
Day 1 18:00 - RabbitMQ 恢复
Day 1 19:30 - outbox 清空
Day 2 09:00 - 突然新任务投递失败？
    → 原因：昨天的 outbox 清空时触发了大量重试
    → 消费者忙于处理重复投递的老任务
    → 新任务排队等待
```

#### 改进建议

**明确 outbox 的 SLA**：

```go
// outbox 表的生命周期
type TaskOutbox struct {
    ID        uint64
    Status    string    // pending / sent / confirmed / dead
    CreatedAt time.Time
    DeadlineAt time.Time  // 新增：deadline = created + 24h
}

// 规则：
// 1. pending → sent 最多 5 分钟（否则发 alert）
// 2. sent → confirmed 最多 10 分钟（否则重投）
// 3. 若 created_at < now()-24h 且 status != confirmed → 发送到 DLX（不再重试）

// 监控告警：
// - outbox.pending 行数 > 100 → 告警
// - outbox 表增长率 > 100 rows/min → 告警
// - 某条消息 retry_count > 10 → 自动 dead letter
```

### 缺陷 5：重试策略与死信队列的模糊边界（严重性：⭐⭐⭐）

#### 问题描述

6.3 说"指数退避重试 3 次，仍失败进死信"。但没有定义：

1. **什么时候重试，什么时候 dead letter？**

   ```
   失败类型 A: LLM timeout
     → 重试（可能短时故障）
   
   失败类型 B: LLM 返回 400（Prompt 格式错）
     → dead letter（不会因重试而好）
   
   失败类型 C: 数据库连接失败
     → 重试（可能网络抖动）
   
   失败类型 D: 数据库 SQL 语法错
     → dead letter（不会因重试而好）
   
   现有设计：全部一样处理（重试 3 次 → dead letter）
   ```

2. **死信队列的处理流程不明确**

   ```sql
   -- 消息进 DLX 后怎么办？
   -- 文档里没说，现有代码中也没有
   
   -- 可能的做法：
   -- A. 消息存 DLX 表，人工审查后重投
   -- B. DLX 消息自动转 review_logs，告知人工
   -- C. 直接丢弃，记指标
   
   -- 都没说清楚
   ```

3. **重试次数是固定的还是指数级的？**

   ```
   文档说"指数退避"，但：
   - 第 1 次失败：等待 1s 后重试
   - 第 2 次失败：等待 2s 后重试
   - 第 3 次失败：等待 4s 后重试
   - 第 4 次及以后：进 DLX
   
   但若连续 DLX 了 100 条消息怎么办？
   - 每条都立即重投？
   - 还是批量等待人工审查？
   ```

#### 改进建议

**明确的重试矩阵**：

```go
// internal/mq/retry.go

type ErrorCategory string

const (
    // 临时错误，应该重试
    ErrorTemporary ErrorCategory = "temporary"
    // 永久错误，不应重试
    ErrorPermanent ErrorCategory = "permanent"
)

func CategorizeError(err error, context string) ErrorCategory {
    // 按类型判断是否可重试
    
    // 临时错误：网络、timeout、熔断
    if isNetworkError(err) || isTimeoutError(err) {
        return ErrorTemporary
    }
    
    // 永久错误：参数错误、业务逻辑错
    if isValidationError(err) || isBusinessLogicError(err) {
        return ErrorPermanent
    }
    
    // 数据库相关：区分
    if isDatabaseError(err) {
        if isConnectionError(err) || isLockTimeout(err) {
            return ErrorTemporary  // 连接错误可能恢复
        }
        if isSyntaxError(err) || isConstraintError(err) {
            return ErrorPermanent  // 语法错误不会好
        }
    }
    
    return ErrorTemporary  // 默认重试
}

// 重试策略
func GetRetryStrategy(category ErrorCategory, retryCount int) RetryStrategy {
    if category == ErrorPermanent {
        return &ImmediateDeadLetterStrategy{}
    }
    
    if retryCount < 3 {
        // 指数退避：1s, 2s, 4s
        delay := time.Duration(1<<uint(retryCount)) * time.Second
        return &ExponentialBackoffStrategy{Delay: delay}
    }
    
    return &SendToDeadLetterStrategy{}
}
```

**死信队列的处理**：

```go
// 定期检查 DLX（死信队列）中的消息
func ProcessDeadLetterQueue() {
    messages := rabbitMQ.GetDeadLetters()
    
    for msg := range messages {
        // 分析原因
        category := analyzeFailureReason(msg)
        
        if category == TransientFailure {
            // 短期故障恢复了 → 重新投入主队列
            rabbitMQ.PublishToMainQueue(msg)
        } else if category == PermanentFailure {
            // 永久失败 → 记录到数据库供人工审查
            db.SaveDeadLetter(&DeadLetterLog{
                TaskID:  msg.TaskID,
                Error:   msg.Error,
                Context: msg.Context,
            })
            
            // 更新任务状态
            db.UpdateTaskStatus(msg.TaskID, "dead", msg.Error)
        }
    }
}
```

## 14.3 权限与数据隔离的问题

### 缺陷 6：教程集的数据隔离不完整（严重性：⭐⭐⭐⭐）

#### 问题描述

12.3.2 说 editor 只能编辑自己导入的教程集下的卡片。但问题是：

1. **"自己导入"的定义不清**

   ```sql
   -- tutorial_sets.created_by = user_id
   
   但如果：
   - editor A 导入了教程集 1
   - editor A 被删除或禁用了
   - editor B 能否访问这个教程集？
   
   -- 当前没有规则
   ```

2. **跨集合的卡片搜索无权限检查**

   ```go
   // GET /cards?keyword=xxx
   // 这个接口应该返回什么？
   
   // 当前设计：
   // - viewer: 所有 published 的非 research-only 卡片（跨教程集）
   // - editor: 自己导入的教程集下的卡片（跨集合筛选）
   // - admin: 所有卡片
   
   // 问题：editor 搜索时，能搜到别的 editor 导入的卡片吗？
   // 文档没说，代码也没有实现这个逻辑
   ```

3. **批量操作时没有权限检查**

   ```go
   // 假设支持批量发布接口（虽然文档没提，但很可能实现）
   // PUT /cards/batch/publish
   // Body: { card_ids: [1, 2, 3, ...] }
   
   // 代码如果这样做：
   db.Model(&Card{}).Where("id IN ?", cardIDs).Update("status", "published")
   
   // 没有检查这些卡片是否都属于当前用户！
   // editor A 可能会发布 editor B 的卡片
   ```

4. **导入权限的缺失**

   ```
   谁可以导入新教程集？
   - 文档说 editor 可以
   - 但没有说教程集的上限
   
   假设恶意用户导入 10000 个教程集
   - 占用存储空间
   - 拖累列表查询性能
   - 没有配额管理
   ```

#### 改进建议

**方案 A：引入教程集级别的权限表**

```sql
CREATE TABLE `tutorial_set_permissions` (
    `id` BIGINT UNSIGNED PRIMARY KEY,
    `set_id` BIGINT UNSIGNED NOT NULL,
    `user_id` BIGINT UNSIGNED NOT NULL,
    `permission` VARCHAR(32) NOT NULL,  -- read / write / admin / share
    `granted_by` BIGINT UNSIGNED,  -- 谁授权的
    `created_at` DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY `uk_set_user_perm` (`set_id`, `user_id`, `permission`)
);

-- 规则：
-- editor 导入集 1 → (set_id=1, user_id=editor_A, permission=write)
-- editor 编辑集 1 下的卡片 → 检查 (set_id=1, user_id=?, permission=write)
-- 导出集 1 → 检查 (set_id=1, user_id=?, permission=read)

-- 权限委托：
-- admin 可以把集 1 的 write 权限授予 editor B
-- 触发 INSERT INTO tutorial_set_permissions
```

**方案 B：批量操作前的权限检查**

```go
// PUT /cards/batch/publish

func BatchPublishCards(cardIDs []uint64, userID uint64) error {
    // 步骤 1：查出所有卡片所属的教程集
    cards := db.GetCardsByIDs(cardIDs)
    setIDs := extractSetIDs(cards)
    
    // 步骤 2：检查用户对所有教程集都有 write 权限
    for setID := range setIDs {

        }

    for card := range cards {
        // 单条检查置信度 & 状态
        if card.Status != "draft" {
            return errors.New("卡片已发布，无法重复发布")
        }
        if card.Confidence < 0.80 {
            // editor 权限可能有限制
        }
    }
}
```

### 缺陷 8：Agent 配置的版本管理缺失（严重性：⭐⭐⭐）

#### 问题描述

3.2 的 `agent_configs` 表：

```sql

    `agent_name` VARCHAR(32) PRIMARY KEY,
    `model` VARCHAR(64) DEFAULT 'deepseek-chat',
```

缺陷：

1. **配置变更没有历史记录**

   ```
   假设：
   - 某天把 temperature 从 0.10 改为 0.05
   - 结果卡片质量变差
   - 想回滚，但不知道之前是 0.10 还是 0.08
   ```

2. **配置的生效时机不明**

   ```
   改 agent_configs 表后：
   - 是否立即对新投递的任务生效？✓（现有设计）
   - 进行中的任务要不要重新配置？✗（不清楚）
   - 已完成的任务的配置怎么查？✗（无审计）
   ```

3. **A/B 测试无法进行**

   ```
   想测试"temperature 0.10 vs 0.05"哪个更好
   但 agent_configs 是 PRIMARY KEY = agent_name
   只能存一套配置
   
   无法同时运行两个版本的 Agent
   ```

**配置版本表**：

```sql
-- 每次改 agent_configs 时：
-- 1. 保存新配置到 agent_config_history
-- 2. 新投递的任务记录配置版本
-- 3. 完成时能查出用的是哪个版本

CREATE TABLE `agent_tasks` (

    `config_version` INT,  -- 新增：记录用的是哪个配置版本
    ...
```

## 14.5 生产环境的风险场景

### 缺陷 10：灾难恢复计划不完整（严重性：⭐⭐⭐⭐）

#### 问题描述

9.9 说"每日全量 mysqldump + binlog 增量"，但没有说：

1. **RTO 目标多少？**（Recovery Time Objective）
   - MySQL 从备份恢复需要多久？
   - 在此期间用户无法使用系统

2. **RPO 目标多少？**（Recovery Point Objective）
   - 最多能丢失多少时间的数据？
   - binlog 保留 7 天，是否足够？

3. **分层灾难的恢复**

   ```
   场景 A：单个卡片数据错了
     → 恢复某条 INSERT，其他数据不变
     → 需要逐行恢复
   
   场景 B：整个教程集错了
     → 恢复整个教程集的所有卡片
     → 需要事务级恢复
   
   场景 C：用户误删了教程集
     → 7 天内软删可恢复（见 12.9）
     → 7 天后无法恢复
   
   场景 D：MySQL 整库宕掉
     → 从 backup 恢复
     → 需要 PITR（point in time recovery）
     → 但文档没说支持不支持
   
   都没有对应的恢复流程
   ```

4. **多区域灾备**

   ```
   现有设计：单机 docker-compose（开发）+ 单数据中心（生产）
   
   无：
   - 跨地域复制
   - 读写分离
   - 灾难时的主从切换
   ```

#### 改进建议

**RTO / RPO 的明确承诺**（见 11.1，但需展开）：

```markdown
# 灾难恢复 SLA

## 恢复目标

| 故障场景 | 影响范围 | RTO | RPO | 恢复方案 |
|---------|--------|------|------|--------|
| 单条卡片数据错 | 1 条 | 15 min | 0（精确到秒） | PITR 恢复单行 |
| 整个教程集错 | ~500 条 | 30 min | 5 min | PITR 恢复到 N-5min |
| MySQL 主库宕 | 全站 | 2 min | <1 min | 自动故障转移 + read replica |
| 数据中心火灾 | 全站 | 4 hour | 1 hour | 跨地域恢复 |
| 用户误删教程集 | 该集 | 1 min | 0 | 软删恢复（7 天内） |

## 恢复演练

每季度执行一次（记录在 docs/reviews/）：
- [ ] 从备份恢复单条数据（PITR）
- [ ] 从备份恢复整个数据中心
- [ ] 验证 RTO / RPO 是否满足承诺
```

## 14.6 扩展性的局限

### 缺陷 11：新 Agent 的集成流程过于繁琐（严重性：⭐⭐）

#### 问题描述

8.3 说"Agent 插件化：统一接口，注册即生效"。但实际需要：

1. 在 `agent_configs` 表添加行
2. 编写 Agent 代码
3. 在编排器里注册
4. 补充 Prompt 文件
5. 修改 Card Schema（如果有新字段）
6. 改置信度计算公式（如果新 Agent 影响打分）
7. 改前端展示（如果有新字段）
8. 补充测试用例
9. 更新文档（12.2 的维度表）

**不是"即插即用"，而是改动很多地方**。

#### 改进建议

**Agent 插件包标准**：

```
plugins/my_new_agent/

├── prompt.md

├── metadata.yaml      # 配置依赖
│   impact_on:
│     - confidence_dimensions: ["temporal"]  # 影响这些维度
│     - new_card_fields: ["my_new_field"]   # 新增字段
│     - breaking_changes: []
└── README.md
```

**自动注册**：

```go
// 启动时扫描 plugins/ 目录
func registerPlugins() {

}
```

### 缺陷 12：教程集的业务模式局限（严重性：⭐⭐）

#### 问题描述

系统只支持"导入 → 处理 → 导出"的单向流。但实际业务可能需要：

1. **多轮迭代**
   ```
   第 1 轮：导入 100 条教程
   第 2 轮：用户反馈不好，要求重新处理
   第 3 轮：改了 Prompt，重新运行
   
   现有设计支持 re_structurize（见 1.1），
   但无法追踪"这是因为 Prompt 改了还是数据改了"
   ```

2. **部分重处理**
   ```
   100 条教程中，只有 20 条不满意
   想只重新处理这 20 条，而不是全部 100 条
   
   现有 API: POST /tasks （针对整个教程集）
   没有：POST /tasks/selective （针对部分卡片）
   ```

3. **增量导入**
   ```
   教程网站每周更新 10 条新教程
   第 1 周导入 100 条集 A
   第 2 周想导入 10 条新教程，追加到集 A
   
   现有设计：每次导入都是新教程集
   无法追加到已有的集
   ```

#### 改进建议

**教程集的版本控制**：

```sql
-- 表设计变更
ALTER TABLE tutorial_sets ADD COLUMN (
    parent_set_id BIGINT UNSIGNED,  -- 父版本
    iteration INT,  -- 第几轮迭代
    change_reason VARCHAR(255),  -- 为什么重新处理
);

-- 示例：
-- Set 1 v1: 100 条教程，第 1 轮
-- Set 1 v2: parent = Set 1 v1，Prompt 改进，第 2 轮
-- Set 1 v3: parent = Set 1 v2，追加 10 条新教程，第 3 轮
```

**选择性重处理 API**：

```go
// POST /tasks/selective
type SelectiveRestructureRequest struct {
    CardIDs []uint64  // 只处理这些卡片
    Agents []string   // 只跑这些 Agent
    Prompt PromptOverride
}

// 例：清洗 + 重新打分，不改材料/工具
POST /tasks/selective
{
    card_ids: [1, 2, 3, ...],
    agents: ["clean", "quality"],
    prompt: { ... }
}
```

## 14.7 运营与成本问题

### 缺陷 13：Token 成本的管理无设计（严重性：⭐⭐⭐）

#### 问题描述

11.4 计算了成本模型（6 次 LLM 调用 per 教程），但没有：

1. **每个账户的成本上限**
   ```
   恶意用户可能：
   - 导入 10000 个超长文本教程集
   - 每条 token 消耗 100k
   - 总成本：10000 × 100k × 6 = 6 亿 token ≈ $600k
   
   无任何配额限制，可以白嫖公司额度
   ```

2. **成本的实时监控**
   ```
   没有说"每天成本多少"的报表
   没有说"成本告警"的规则
   无法及时发现异常消耗
   ```

3. **模型切换时的成本对比**
   ```
   DeepSeek: 便宜（input 0.1¥/M token, output 0.2¥/M token）
   GPT-4: 贵（input $3/M token, output $6/M token）
   豆包: 中等
   
   文档没有说"什么时候该切换模型"
   没有成本 vs 质量的权衡矩阵
   ```

#### 改进建议

**用户配额与成本管理**：

```sql
CREATE TABLE `user_quotas` (
    `user_id` BIGINT UNSIGNED PRIMARY KEY,
    `daily_token_quota` INT,  -- 每天最多消耗多少 token
    `monthly_cost_limit` DECIMAL(10,2),
    `current_month_cost` DECIMAL(10,2),
    `created_at` DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 规则：
-- editor: daily_quota = 10M token / 月支出 ≤ $100
-- admin: unlimited

-- 消费时检查：
if currentDayTokens + estimatedTokensForTask > dailyQuota {
    return 403 "Daily quota exceeded"
}
```

## 最后的话

这 13 个缺陷反映了一个普遍现象：

> **文档完整度 ≠ 设计完整度**

即使文档从 8.1 改到 9.5，设计本身仍有**结构性问题**：
- 置信度系统的可信度链条太长
- Agent 间的语义耦合隐患
- 权限隔离的细节缺失

这些**需要在需求阶段就明确**，而不是后期修补。
