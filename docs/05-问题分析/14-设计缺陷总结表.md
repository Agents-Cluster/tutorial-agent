# 设计缺陷快速查阅表

> 13 个设计缺陷的一页纸总结，按优先级排列

---

## 🔴 P1 必须在代码开发前修复（6 个）

### 缺陷 2：Agent 语义不对齐 ⭐⭐⭐⭐
**问题**：步骤 Agent 说"纸张"，材料 Agent 说"牛皮纸"，质检无法判断是否重名  
**后果**：低置信卡片进不必要的人工复核；置信度系统变成"LLM 一致性检查"而非"质量检查"  
**修复**：编排器里补充归一化映射层（不破坏并行，耗时不增加）

### 缺陷 6：数据隔离不完整 ⭐⭐⭐⭐
**问题**：editor 能跨越权限边界查看/编辑其他 editor 的卡片；批量操作没权限检查  
**后果**：数据泄露、误操作；可能导致法律问题  
**修复**：补充教程集权限表 + 批量操作前的权限检查 + 导入配额

### 缺陷 10：灾难恢复计划不完整 ⭐⭐⭐⭐
**问题**：文档说"每日备份"但没定 RTO/RPO；无 PITR（按时间点恢复）规则  
**后果**：真正宕机时不知道能恢复到什么程度；可能丢失关键业务数据  
**修复**：定 RTO/RPO SLA 表 + PITR 恢复流程 + 季度演练清单

### 缺陷 1：置信度系统信息丢失 ⭐⭐⭐
**问题**：质检 Agent 本身不稳定（漏判/误判），但代码打分完全依赖它  
**后果**：置信度虚高或虚低；低质量卡片混入库；复核队列误导  
**修复**：质检 Agent 预热阶段校验准确率，或引入双质检/专家评分

### 缺陷 3：卡片版本化设计缺陷 ⭐⭐⭐
**问题**：重跑时 `is_current` 的唯一性保证有竞态条件；软删与版本化交互不明  
**后果**：并发重跑时任务失败；删除后恢复不清楚该恢复哪个版本  
**修复**：加分布式锁保证互斥 + 明确恢复策略（仅恢复最新版本）

### 缺陷 13：Token 成本无管理 ⭐⭐⭐
**问题**：无用户配额限制、无实时成本监控、无成本告警  
**后果**：恶意用户可能白嫖公司的 LLM 额度（单次百万级 token）；成本失控  
**修复**：加用户配额表 + 消费时检查 + 每日成本报表

## 🟡 P2 强烈建议在代码阶段并行实现（5 个）

### 缺陷 4：Outbox 超时无限制 ⭐⭐⭐
**问题**：消息进 outbox 后没有 deadline；积压无界限；重投没终止条件  
**后果**：RabbitMQ 故障时积压数量无法预测；恢复后大量冗余投递  
**修复**：定 Outbox SLA（pending < 5min → alert，24h 无 confirmed → dead letter）

### 缺陷 5：重试/死信的模糊边界 ⭐⭐⭐
**问题**：不区分"临时失败"vs"永久失败"；死信队列的处理流程无说明  
**后果**：参数错误的任务也重试 3 次浪费成本；死信消息无法追踪  
**修复**：明确错误分类矩阵 + 死信处理流程 + 人工审查机制

### 缺陷 8：Agent 配置版本管理缺失 ⭐⭐⭐
**问题**：改 temperature 或 Prompt 后无历史记录；无法进行 A/B 测试  
**后果**：无法对比不同配置的效果；配置变更无审计  
**修复**：加 agent_config_history 表 + 配置快照 + A/B 测试支持

### 缺陷 7：复核权限未明确 ⭐⭐
**问题**：reviewer 角色权限不清；复核员能改什么/不能改什么无界限  
**后果**：复核员可能滥用权限；无法评估复核员的质量  
**修复**：定 reviewer 角色 + 复核权限矩阵 + 复核修改审计链

### 缺陷 9：监控告警不完整 ⭐⭐
**问题**：定了很多指标但没定告警阈值；无法自动告警  
**后果**：依赖人工观察大盘，容易漏掉问题  
**修复**：补充 alerts.yaml，定每个指标的告警阈值与触发动作

## 🟢 P3 后期改进（2 个，不影响 v1 发版）

### 缺陷 11：Agent 插件化不够 ⭐⭐
**问题**：新增 Agent 需要改代码多处；不是真的"插件化"  
**后果**：新 Agent 集成复杂；扩展性受限  
**修复**：定标准的 Agent 包格式 + 自动注册机制

### 缺陷 12：教程集模式局限 ⭐⭐
**问题**：只支持"导入→处理→导出"单向流；无多轮迭代、无增量导入  
**后果**：用户反馈不满意时无法部分重处理  
**修复**：教程集版本控制 + 选择性重处理 API

```
Week 1-2 (代码开发启动前)：
  ✅ 决策缺陷 2, 6, 10, 1, 3, 13 的解决方案
  ✅ 更新文档（加入修复方案）
  ✅ 设计数据表变更

Week 3+ (代码开发阶段)：
  ✅ 实现 P1 缺陷的修复
  ✅ 并行实现 P2 缺陷的改进
  ⏳ P3 缺陷留到 v1.1

Month 3+ (系统稳定运行后)：
  📅 根据实测反馈改进 P2/P3 缺陷
```
