# 06 - 异常处理设计

> 本文档包含：任务状态机、重试策略、幂等机制、死信队列、熔断降级、限流控制。

---

## 6.1 任务状态机

```
pending(待排队) → running(处理中) → succeeded(成功)
                       │
                       ▼
                   failed(失败) ──重试N次──→ dead(死信)
```

- Agent 子任务（agent_items）各自独立状态：清洗成功 ≠ 质检成功；
- 质检失败可**只重试质检 Agent**，不需要重新拆解（省时省钱，面试亮点）。

### 6.1.1 任务终态判定规则（`succeeded` / `failed` / `dead` 各自由谁写入）

状态机只画了箭头，没写"什么条件走哪条边"，这里补齐——**否则 `failed` 是一个没有入边的僵尸状态**。

| 终态 | 写入者 | 判定条件 | 后续动作 |
| --- | --- | --- | --- |
| `succeeded` | 任务汇总协程 | 全部 `agent_items` 进入终态，且 `success_items > 0`（有卡片产出） | 结束。`failed_items > 0` 时前端展示"部分成功"（6.6-3），不回滚、不重跑全批 |
| `failed` | 任务汇总协程 | 全部 `agent_items` 进入终态，但 `success_items = 0`（整批零产出，典型如 API Key 失效、教程集被删） | **可恢复**：`POST /tasks/{id}/retry` 把子任务改回 `pending`，任务回到 `running`（4.3.3） |
| `dead` | 任务汇总协程 | `success_items = 0` 且任务级重试次数 > `LLM_MAX_RETRY` | **不可自动恢复**：只能重建任务；`GET /tasks/{id}` 返回最后一次 `error_summary` |

两条硬约束：
1. **`succeeded` 不要求零失败**：一批 100 条成功 70 条仍是 `succeeded`（部分成功），只有"一条都没产出"才是 `failed`——否则 30 条失败会让 70 张卡片的成本作废；
2. **`failed` 必须可退出**：它是"整批失败但还没放弃"的中间态，不是终点；`dead` 才是终点。前端按 `status` + `failed_items` 两个字段组合显示（`succeeded` + `failed_items>0` = 部分成功）。

## 6.2 关键异常处理设计点

| 设计点 | 方案 | 解决什么问题 |
| --- | --- | --- |
| 客户端幂等 | `(user_id, idem_key)` 唯一约束，Header 传 `Idempotency-Key` | 用户手抖点两次，不会重复创建任务、重复扣费 |
| 投递补偿 | 本地消息表 outbox：写 MySQL + 写 outbox 同一事务，后台协程扫 outbox 投 MQ | "写库成功但 MQ 投递失败"的窗口不会丢任务 |
| 消费幂等 | Redis 标记 `key=task_no:tutorial_id:agent_name`，**该 Agent 成功后写，TTL=7天** | MQ 重复投递导致重复调用 LLM 重复扣费；失败路径不留标记，可重试 |
| 分布式锁 | Redis SETNX，锁 `task_id`，带续期 | 多实例部署任务被多个消费者抢到 |
| 死信队列 | RabbitMQ DLX，多次失败转死信 | 失败任务不无限重试、不丢失，可人工介入 |
| 重试策略 | 指数退避（1s/2s/4s）+ 最大 3 次 | 不把第三方 LLM API 打爆 |
| 熔断 | 连续失败达阈值（`LLM_CIRCUIT_BREAK_THRESHOLD`，见 9.2）后熔断，窗口 `LLM_CIRCUIT_BREAK_WINDOW` | 第三方 API 挂掉时保护系统 |
| 降级 | 熔断期间**任务保持 `pending`、不空转不失败**，窗口结束自动续跑（与 8.2.1 的降级矩阵同一口径；单次调用失败仍按重试/死信处理） | 单个 Agent 故障不影响全局，也不把可恢复的失败固化成终态 |
| traceId 传递 | 生产者写 AMQP message headers，消费者读取恢复 context | 全链路日志可追踪，跨进程不断 |

**熔断与重试的接管时序（衔接 8.2.1 与 10.6.5）**：重试协议与熔断不是并行发生——初次失败先走 1s/2s/4s 指数退避、最多 3 次；连续失败达 `LLM_CIRCUIT_BREAK_THRESHOLD` 触发熔断后，**新子任务不再进入重试协议**，直接挂起保持 `pending`，窗口结束自动续跑；熔断**之前**已耗尽重试进入死信的子任务保持死信，由 `POST /tasks/{id}/retry` 人工恢复（4.3.3）。没有这层接管，LLM 100% 超时下任务会在约 12s 内全部死信，本表"熔断期间任务保持 pending"与 8.2.1"恢复后自动续跑"就兑现不了。

### 6.2.1 为什么消费幂等键必须带 `agent_name`

如果键只到 `task_no:tutorial_id`，会出现一个自相矛盾的场景：第 37 条教程的 `material` 成功、`step` 失败。重试 `step` 前先查标记 → 命中（`material` 成功时已写）→ 直接跳过 → **失败子任务永远修不好**。而 6.2 又承诺"子任务独立重试"。

带上 `agent_name` 后，键的粒度 = `agent_items` 唯一键 `(task_id, tutorial_id, agent_name)` 的粒度，幂等与重试才自洽。

两条配套约束：
1. 标记在**该 Agent 成功落库之后**写，失败路径不写（否则重试被自己挡住）；
2. TTL 7 天，覆盖"最长重试窗口 + 人工介入窗口"；过期后若再收到重复消息，由数据库唯一键兜底（同 `card_version` 覆盖写）。

## 6.3 Outbox 本地消息表机制

**为什么需要 outbox**：直接写库后投 MQ，存在"写库成功但 MQ 投递失败"的窗口，导致任务丢失。

**方案**：
1. 同一事务内：写 `agent_tasks` + 按"教程数 × 启用 Agent 数"写 `agent_items` + 写 `task_outbox`（status=pending）；
2. 后台投递协程用 `SELECT ... FOR UPDATE SKIP LOCKED` 抢占 outbox（status=pending），投 MQ 成功后标 `sent`——多实例部署也不会重复投递；
3. **消息体必须携带 `outbox_id`**，消费者在 ACK 前用它把该行标为 `confirmed`；不带 `outbox_id` 就无法闭环，只能靠时间猜测；
4. 兜底定时任务：扫 `status=pending AND created_at < now-5min` 重新投递；
5. 观测：`outbox_pending_total` 持续 > 100 或 `outbox_oldest_age_seconds` > 600 时触发巡检（指标见 9.4.1）。注意此处"巡检"= Grafana 大盘阈值线 + 人工查看，自动推送尚未做（10.11 第 4 条）。

## 6.4 DLX 死信队列配置

```bash
# 死信交换机 + 死信队列
rabbitmqadmin declare exchange name=agent_dlx_exchange type=direct
rabbitmqadmin declare queue name=agent_dlq_queue
rabbitmqadmin bind queue=agent_dlq_queue exchange=agent_dlx_exchange routing_key=dlq

# 业务队列配置死信转发
rabbitmqadmin declare queue name=agent_p0_queue \
  arguments='{"x-dead-letter-exchange":"agent_dlx_exchange","x-dead-letter-routing-key":"dlq"}'
# P1/P2 队列同理
```

## 6.5 并发与资源控制策略

| 控制项 | 策略 | 阈值 |
| --- | --- | --- |
| 单用户并发任务 | 限制同时进行中的任务数 | 默认 5 个 |
| 全局并发消费者 | P0/P1/P2 独立消费者池（合计 4 个协程） | P0=2, P1=1, P2=1 |
| LLM API 限流 | 全局信号量 + 令牌桶 | `LLM_MAX_CONCURRENT` 默认 **20**（推导见 6.5.1） |
| 队列堆积保护 | 超过阈值触发巡检（大盘阈值线，非自动推送，见 9.4.1 与 10.11-4） | 积压 > 1000 条 |

### 6.5.1 为什么 `LLM_MAX_CONCURRENT` 必须 ≥ 16（信号量与消费者数的乘积关系）

8.1.3 说"与 4 个消费者的乘积关系见 6.5"，这段就在这里补上：

```
需求并发 = 消费者数 × 单条并行路数 = 4 × 4 = 16
```

单条教程在处理期间，同时可能有 4 个 LLM 请求在飞（材料/工具/步骤/风险）。消费者是 4 个，所以**峰值并发是 16**。信号量小于 16 时，多出来的请求在信号量上排队，单条墙钟时间被拉长，8.1.1 的 15s 模型随之失效。

按"请求秒"算更准（单条教程消耗的 LLM 请求时间之和）：

```
单条请求秒 = 清洗 4s + 四路并行 6s×4 + 质检 5s = 33 请求秒
日吞吐上限 = S × 有效工时 / 33 × 利用率
```

| `LLM_MAX_CONCURRENT` | 日吞吐上限（8h × 0.7） | 瓶颈 |
| --- | --- | --- |
| 5 | 5 × 28 800 / 33 × 0.7 ≈ **3 050/天** | 信号量（P5 的 5 000 达不到） |
| 16 | 16 × 28 800 / 33 × 0.7 ≈ 9 770/天 | 消费者数（≈5 300/天，见 8.1.2） |
| **20（默认）** | 同上，不成为瓶颈 | 消费者数；留 4 个额度给同步接口与重试 |

**结论与前置条件**：
1. 默认 20 = 16（峰值） + 4（同步接口/重试余量）；
2. **S 必须与上游配额对齐**：若第三方 API 的并发配额 < 20，就按配额设 S，并用上式重算 P5——不要一边写 5 000/天、一边只给 5 个并发；
3. 信号量是**进程内**实现，不依赖 Redis——所以 8.2.1 里 Redis 不可用时只降级"限流计数器"，信号量照旧生效；否则 LLM 上游会被瞬间打爆。

## 6.6 降级策略

> **组件级降级矩阵的唯一权威在 8.2.1**（LLM / Redis / MQ / MySQL / MinIO 各自故障时怎么办），本节只写**流水线内部**的降级，不复制矩阵。

1. **Agent 独立降级**：任一 Agent 可关（`agent_switches`），卡片缺该字段并按 5.4.2 扣分，主流程不断；
2. **质检降级**：质检 Agent 连续 3 次失败 → 该条按 `confidence = 0` 处理并**强制进人工复核**，绝不自动入库；
3. **部分成功**：一批 100 条中 30 条失败时，任务仍可 `succeeded`（`failed_items > 0` 时前端显示"部分成功"），**不整批回滚**——已产出 70 张卡片的成本不能因为 30 条失败而作废；
4. **不降级的底线**：幂等与审计不降级。宁可任务卡住等人处理，也不能在"跳过幂等"的模式下继续跑（会重复扣费）。

## 6.7 完整异常链路口述（面试版）

> **幂等键防重复提交 → outbox 保投递不丢 → 队列削峰 → 锁+消费幂等保唯一 → Agent 子任务独立成败 → 失败进死信 → 置信度分流人机协同。**
>
> 关键阈值：LLM 重试最大 3 次、指数退避 1s/2s/4s、P0/P1/P2 三级优先级、置信度阈值 0.8。
