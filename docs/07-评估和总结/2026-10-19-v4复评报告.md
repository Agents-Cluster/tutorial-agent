# v4 复评报告（独立重审）

> 评审对象：`docs/` 下 01–11 + `baseline.md` + `prompts/`（共 4725 行）
> 评审标准：`评分标准.md`（10 维度 × 100）
> 评审方式：**不采信 v3 的自评结论**，从零取证，逐项验算；发现冲突先修，修完再评。
> 日期：2026-10-19

## 一、结论先说

**v3 自评 95 分是不成立的。按标准重审，未修改前实际 82 分（B 级）——硬性否决项命中 5 次，而 v3 报告写的是「0 处事实冲突」。**

修完这 5 处后，本轮复评为 **94 分（A 级）**。差的 1 分不是没找到问题，而是**有 3 件事只能在真机上验证**，文档自证不了（见第五节）。

> 一句话：**v3 治好了"文档长得像交付物"，没治好"文档里的事实互相不认账"。**

## 二、未修改前的 5 处硬冲突（含证据）

### P0-1　Card Schema 有三个字段，库里没有落脚点

| 位置 | 承诺 |
| --- | --- |
| `05:137` `05:143` | 卡片 JSON 里有 `confidence_detail`、`quality_flags` |
| `05:154-155` | 明确写「四个维度的分项分数，不只存总分」「由打分函数一并产出」 |
| `04:242` | `GET /cards/{id}` 返回 `raw_text` + `removed_spans` + `confidence_detail` |
| `prompts/clean.md:66` | 「补 `start/end` 后**落库**」 |

**现实**：`03` 的 `cards` 建表语句、`3.1` 表清单、`05` 的 Go struct —— 三处一致地**都没有**这三个字段（`grep -c "confidence_detail\|quality_flags" 03-data-design.md` = **0**）。

后果不是"少个字段"，是三条承诺同时失效：
1. 复核页拿不到分项分，5.4.2 那套"可定位扣分原因"的设计无法呈现；
2. `removed_spans` 无处可存，"清洗误删可一键展开原文"这个防信息丢失的卖点直接落空；
3. 照文档建表再写代码，第一步就 `Unknown column`。

**判据**：D3-5 模型一致（15 分）归零 → 命中硬性否决项 3（同一字段两处不一致）。

### P0-2　把没做的实验写成了既成事实

| 位置 | 原文 | 与什么冲突 |
| --- | --- | --- |
| `10:42`（Q3） | 「0.8 这个阈值是在 200 条人工标注样本上做 precision-recall 曲线定的」 | `11.2` R5 状态 = **TBD** |
| `10:50`（Q5） | 「做了单轮 LLM baseline 对照，**用数据证明**多 Agent 优于单轮」 | `11.2` R1–R4 全 TBD；`baseline.md` 全 TBD |
| `10:374`（已知缺陷） | 「阈值 0.8 是在 200 条样本上标定的」 | 同上 |

同一份文档里，`10:34`（Q1）刚写完「**召回率提升幅度以 11.2 的登记结果为准——没测出来之前，我不会说具体百分点**」，翻八行就自证"用数据证明"。这是面试里最容易被追死的一类：面试官只要问"那组数据给我看看"，前面所有"诚实"的表述全部作废。

**判据**：命中硬性否决项 2（结论位置把预期写成实测）。

### P0-3　熔断后任务是什么状态，两处答案相反

- `06:29`（原）：熔断后**任务标记失败**
- `08:64`：LLM 整体不可用 → 熔断 60s，**任务保持 `pending` 不空转，恢复后自动续跑**

一个是终态，一个是可恢复态。开发照着写，两种实现都能"符合文档"，但行为完全不同：前者把一次可恢复的抖动固化成失败，后者才是 8.2.1 承诺的"不丢任务"。

**判据**：命中硬性否决项 3。

### P0-4　部署脚本硬编码密码，与自己的验收标准打架

`09` 里 4 处 `-uroot -proot123`（`117`/`350`/`471`/`478`），`rabbitmqadmin -u admin -p admin123` 10 处，compose 里 MinIO 凭据也写死。而同一份文档：

- `7.7` 第 2 项门禁：「MySQL / RabbitMQ / MinIO 默认密码已改」
- `10.6.2` 工程质量验收：「密钥、配置全部环境变量，**无硬编码**」

按门禁改了密码，`init.sh` 立刻连不上库——**这条门禁自己的检查项，会把初始化脚本弄挂**。

**判据**：D8-2 配置（15 分）重扣；与 D10-3 单一事实源同源。

### P0-5　引用了不存在的接口

`08:109`：「前端从 `/api/v1/meta/enums` 拉取」，用于"文案与枚举单一来源"。但 `04:36-61` 的接口清单 24 个里没有这个接口。

**判据**：命中硬性否决项 1（指向不存在的东西）。这条虽小，但它恰好否掉了 8.4 里"枚举不会各写一套"这个可验证性主张——承诺了一个不存在的验证手段。

## 六、遗留风险（文档自证不了的 3 件事）

1. **`minio/mc` 与 `rabbitmqadmin` 能否在容器里跑，只有真机能证明。** 本报告把它们统一成"一次性 mc 容器"的写法（比 `exec` 进 minio 更稳），但 `rabbitmq:3.13-management` 镜像是否自带 python3（`rabbitmqadmin` 的运行时）没有实机验证。若跑不通，改用 management HTTP API 或 `definitions.json` 导入，只需改 9.3 一个脚本。
2. **R1–R9 仍是 TBD。** 这不是文档缺陷，是项目进度。文档已经做到"没有数据就不编数据"，但它也只能做到这一步——`10.1.3` 的任何一句话，在 R1–R5 填上之前都只能算"设计陈述"。
3. **`PUT /cards/{id}` 与 `POST /tutorial-sets` 只有字段速查，没有完整契约。** 六个写接口里这两个是"编辑器主路径"，缺 body 示例会让前端第一次对接时来问人。

## 七、一句话

**v3 是"看起来能交付"，v4 是"查过账了"。**

这一轮真正值钱的不是补了三个字段，而是换了一种查法：**同一个事实，去全库搜它出现了几次**。五个 P0 里没有一个是"写错了"，全是"各写各的、彼此不认账"——这也正是这份文档从 v1 到现在反复复发的病根。
