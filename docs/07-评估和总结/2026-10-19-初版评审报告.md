# 项目方案文档评审报告

**评审对象**：《DIY 手工教程结构化拆解 Agent 工作站》（飞书 .md，1874 行 / 约 5.4 万字）
**评审日期**：2026-10-19
**评审视角**：技术方案完整度 + 可落地性 + 面试抗追问能力

---

## 〇、总体判断

**优点（先说清楚，别改坏了）**

- 定位非常清楚："只做结构化抽取、不校验教程正确性"这个边界划得漂亮，避免了最大的一个坑。
- 异步链路、幂等、死信、子任务独立重试这一套后端叙事是完整的，比大多数"Agent 项目"扎实。
- 文档结构工程化程度高（40 章，含 SQL / compose / init / 冒烟 / 排障），这个完整度本身就加分。
- "人工复核闭环 + 置信度分流"是正确的产品思路，不是纯炫技。

**但有三类问题必须处理**

| 类别 | 数量 | 影响 |
| --- | --- | --- |
| P0 致命 | 8 项 | 数据模型撑不住已宣称的功能 / 部署跑不起来 / 核心数据结构缺失 |
| P1 一致性 | 12 项 | 前后矛盾，一问就露，显得"文档是拼的" |
| P2 缺失 | 6 项 | 交付物不全，效果无法自证 |

**一句话结论**：这份文档目前是"**架构叙事 90 分，工程规格 55 分**"。它讲清楚了你打算做什么，但没定义清楚"做出来的东西长什么样"。补上第 1、2、3 条（输出 Schema、数据模型、幂等闭环）就能到 80 分。

## 一、P0：必须改，否则会被直接击穿

### P0-1 全文档没有"卡片 Schema"——系统的核心数据结构是空的

**位置**：第十章、19.5、第二十三章都在引用 `materials_json / tools_json / steps_json / risk_json`，但**没有任何一处定义这些 JSON 里面是什么字段**。

这是最严重的问题。理由：

- 没有 Schema，就写不出 Prompt（各 Agent 的输出格式无从约束）；
- 没有 Schema，就写不出质检规则（"字段完整性校验"校验什么字段？）；
- 没有 Schema，导出格式、前端卡片渲染、效果评测的"字段召回率"全部悬空；
- 面试官问"你抽出来的步骤长什么样"，这是第一个问题。

**改法**：在第九章后新增一节《9.5 卡片数据结构（Card Schema）》，并在 `internal/model/card.go` 落成 Go struct。建议：

```json
{
  "tutorial_id": 10231,
  "materials": [
    { "name": "牛皮纸", "spec": "A4 120g", "qty": 2, "unit": "张", "optional": false, "evidence": "原文片段" }
  ],
  "tools": [
    { "name": "美工刀", "required": true, "evidence": "原文片段" }
  ],
  "steps": [
    { "seq": 1, "action": "沿虚线裁切纸张", "uses": ["牛皮纸", "美工刀"], "duration_est": "5min", "warnings": [] }
  ],
  "risks": [
    { "level": "high", "type": "cut", "desc": "使用美工刀裁切", "mitigation": "垫切割垫、戴手套" }
  ],
  "difficulty": { "level": "easy", "reason": "步骤 5 步以内，无高温/明火" },
  "confidence": 0.86,
  "confidence_detail": { "completeness": 0.9, "temporal": 0.8, "grounding": 0.85 },
  "quality_flags": ["tool_missing:打磨"]
}
```

关键设计：每个实体带 `evidence`（原文片段）——这是后面"原文一致性"校验能落地的前提，也让"忠实抽取"这个卖点变得可验证。

### P0-2 数据模型撑不住"任务进度"和"子任务独立重试"

**位置**：第十章表清单 + 第二十三章 SQL + 第十二章异步链路。

三处硬伤：

1. **`agent_items` 缺教程维度**。一个批量任务含 N 条教程 × 6 个 Agent，但 `agent_items(task_id, agent_name)` 只能表达"这个任务的清洗 Agent 跑过一次"，无法表达"第 37 条教程的步骤 Agent 失败"。第十二章反复讲的"子任务独立重试"，在表结构上无法定位要重试哪一条。
2. **`agent_tasks` 无进度字段**。全文到处写"任务进度查询""进度可视化"，但表里没有 `total/success/failed/review` 计数。进度只能全表扫 cards 反推，且卡在途中（未生成卡片）的条目算不出来。
3. **`cards` 无 `task_id`、无版本号**。无法回答"这张卡片是哪次任务产出的"；更严重的是 `UNIQUE KEY uk_tutorial (tutorial_id)` 意味着一条教程只能有一张卡片，而 `agent_tasks.task_type` 里定义了 `re_structurize`（重新拆解）——**重跑必然撞唯一键**，与"拆解结果独立可回滚"（建表要点第 2 条）自相矛盾。

**改法**：

```sql
-- agent_items 改为按 (任务, 教程, Agent) 三元组
ALTER TABLE agent_items
  ADD COLUMN tutorial_id BIGINT UNSIGNED NOT NULL COMMENT '教程记录ID' AFTER task_id,
  ADD COLUMN trace_id VARCHAR(64) DEFAULT NULL,
  ADD COLUMN token_in INT UNSIGNED DEFAULT 0,
  ADD COLUMN token_out INT UNSIGNED DEFAULT 0,
  ADD UNIQUE KEY uk_task_tutorial_agent (task_id, tutorial_id, agent_name);

-- agent_tasks 补进度与统计
ALTER TABLE agent_tasks
  ADD COLUMN total_items INT UNSIGNED NOT NULL DEFAULT 0,
  ADD COLUMN success_items INT UNSIGNED NOT NULL DEFAULT 0,
  ADD COLUMN failed_items INT UNSIGNED NOT NULL DEFAULT 0,
  ADD COLUMN review_items INT UNSIGNED NOT NULL DEFAULT 0;

-- cards 支持版本化 + 溯源
ALTER TABLE cards
  ADD COLUMN task_id BIGINT UNSIGNED NOT NULL COMMENT '产出任务ID',
  ADD COLUMN card_version INT UNSIGNED NOT NULL DEFAULT 1,
  ADD COLUMN is_current TINYINT NOT NULL DEFAULT 1,
  ADD COLUMN created_by BIGINT UNSIGNED DEFAULT NULL,
  DROP INDEX uk_tutorial,
  ADD UNIQUE KEY uk_tutorial_version (tutorial_id, card_version),
  ADD KEY idx_task (task_id);
```

### P0-3 "按材料/工具筛选"是核心卖点，但数据模型做不到

**位置**：第四章第 2 点、第五章功能清单、第十章。

文档把"结构化后支持按难度、工具、材料筛选"当成主要价值，但实现方案是把材料/工具塞进 JSON 列。结果：

- `WHERE JSON_CONTAINS(materials_json, '"美工刀"')` 全表扫，无法走索引；
- 材料名不归一（"美工刀"/"裁纸刀"/"美工小刀"），筛选必然漏；
- 也做不了"用了这个材料的教程有多少"这类统计。

**这是最容易被追问穿的地方**：卖点写了，模型没跟上。

**改法（二选一）**：

- **A（推荐，工作量小）**：保留 JSON 作为展示快照，另建维度表：

```sql
CREATE TABLE card_entities (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  card_id BIGINT UNSIGNED NOT NULL,
  entity_type VARCHAR(16) NOT NULL COMMENT 'material/tool',
  name VARCHAR(64) NOT NULL,
  name_norm VARCHAR(64) NOT NULL COMMENT '归一化后名称',
  spec VARCHAR(128) DEFAULT NULL,
  KEY idx_type_norm (entity_type, name_norm),
  KEY idx_card (card_id)
) ENGINE=InnoDB;
```

抽取时同步写维度表（`name_norm` 用同义词表 + 简单归一规则，不做重量级 NLP）。

- **B**：MySQL 8 生成列 + 多值索引（`CAST(materials_json->'$[*].name' AS CHAR(64) ARRAY)`），能走索引但绑定字段路径，改 Schema 就废。

文档里必须写清楚"JSON 只做展示，筛选走维度表"，否则这一条就是空话。

### P0-4 置信度的"产生方式"自相矛盾，0.8 阈值没有依据

**位置**：9.2（质检 Agent 输出"置信度 + 缺陷清单"）vs 13.2（`confidence = Σ(维度得分 × 权重)`）。

一个说**LLM 直接给分**，一个说**程序加权算分**。这两种实现差别很大：

- 让 LLM 直接输出 0~1 的分数，是已知不可靠做法——同一份输入两次调用可能给 0.82 和 0.61，阈值半分流完全失效；
- 13.2 的四个维度里，"步骤时序合理性"和"原文一致性"又要再调一次 LLM 判断，等于自评自证。

**改法（这条改完，整个质检模块的可信度会上一档）**：

明确写成"**LLM 出证据，程序算分**"：

| 维度 | 计算方式 | 谁做 |
| --- | --- | --- |
| 字段完整性 40% | 规则：materials/tools/steps 是否为空、必填字段是否缺失 | 纯代码 |
| 步骤时序 25% | LLM 只输出 `[{seq_a, seq_b, relation: before/after/invalid}]` 冲突对，程序按冲突数扣分 | LLM 出证据 + 代码算分 |
| 原文一致性 25% | 每个实体 `evidence` 是否能在原文中定位（字符串/模糊匹配命中率），程序算比例 | 纯代码（+LLM 兜底判断矛盾） |
| 文本质量 10% | 规则：长度、噪声符号占比、非教程句比例 | 纯代码 |

同时在 21.4 加一条：**"0.8 阈值通过在 200 条人工标注样本上做阈值-准确率曲线确定，取 precision ≥ 0.9 的最低阈值"**。这句话写上去，比权重表本身更有说服力。

顺带：`cards.status` 的枚举（pending/approved/rejected）与 13.3 的三档分流（≥0.8 / 0.5~0.8 / <0.5）对不上，`<0.5` 那一档没有对应状态；`status` 和 `review_status` 两个字段语义重叠，需重新定义——建议 `status` 只表示卡片生命周期（draft/published/archived），`review_status` 表示人工态（auto_passed/pending_review/reviewed/rejected）。

### P0-5 幂等链路没闭环，会真的重复扣费 / 任务永久卡死

**位置**：10 章设计要点、12.3、28.5（"不做消息事务，用状态表 + 幂等保证最终一致性"）。

三个洞：

1. **`task_no` 由服务端生成，防不住重复提交**。运营手抖点两次"提交任务"，会生成两个不同 task_no、两次全流程 LLM 调用。业务幂等键必须是**客户端传入的 `Idempotency-Key`**，服务端用它做唯一约束。
2. **没有投递补偿**。既然明确"不做消息事务"，那"写 MySQL 成功 + 投 MQ 失败"这一秒的窗口必然存在，任务会永久停在 pending，没有任何机制捞回来。28.5 说"最终一致性"却没给达成手段。
3. **幂等标记的生命周期没定义**。12.3 写"消费前查任务状态 + Redis 去重标记"——如果标记写在处理前、失败后不清除，重试会被自己的标记挡住；如果标记无 TTL，24 小时后内存泄漏。

**改法**（这一段可以直接作为面试亮点讲）：

```sql
-- 1) 客户端幂等
ALTER TABLE agent_tasks
  ADD COLUMN idem_key VARCHAR(64) NOT NULL COMMENT '客户端幂等键',
  ADD UNIQUE KEY uk_user_idem (user_id, idem_key);

-- 2) 本地消息表（outbox），事务内一起写
CREATE TABLE task_outbox (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  task_id BIGINT UNSIGNED NOT NULL,
  payload JSON NOT NULL,
  status VARCHAR(16) NOT NULL DEFAULT 'pending' COMMENT 'pending/sent/confirmed',
  retry_count INT UNSIGNED NOT NULL DEFAULT 0,
  next_retry_at DATETIME DEFAULT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_status_retry (status, next_retry_at)
) ENGINE=InnoDB;
```

流程：`提交任务 + 写 outbox` 同一个事务 → 后台投递协程扫 outbox 投 MQ → 投递成功标 `sent` → 消费者 ACK 后标 `confirmed`。再加一个兜底定时任务：扫 `status=pending AND created_at < now-5min` 的任务重新投递。

幂等标记改成"**只在成功后写，key = task_no + tutorial_id，TTL = 7 天**"，失败路径不留标记。

### P0-6 数据源是空的：没有具体数据集名、规模、许可、语言链路

**位置**：14.1。

" HuggingFace DIY 教程数据集（主源）" —— 没给 dataset id、没给条数、没给字段、没给 license。这是全文档最虚的一处，因为**它是整个项目的地基**。

而且有一个被完全忽略的链式问题：

- HuggingFace 上现成的 DIY / craft 教程数据集**基本是英文**；
- 而 14.2 的关键词粗筛用的是中文词"材料/工具/步骤" → 英文样本会被 100% 误杀；
- 输出卡片是中文（`difficulty: easy/medium/hard` 除外），中间要不要翻译？翻译本身会引入幻觉，且成本翻倍。

**改法**：

1. 明确写死数据集：`dataset_id`、样本量、语言、字段名、license、采样方式（如 `wikihow` 子集 / `instructables` 归档，取 500~1000 条）。若最终找不到合适的公开集，就诚实改为"自建 300 条人工标注种子集 + 公开集补充"，并把标注规范写出来——这反而更可信。
2. 粗筛规则改成**语言无关的多信号**：标题层级数量、列表符号密度、祈使句/动词开头句比例、长度分布、领域词表（中英双语）。
3. 独立一节写《语言策略》：英文原文 → 中文卡片，是"抽取时直接输出中文"还是"先翻译再抽取"，二选一并说明取舍（建议前者：一次调用内完成，省一次调用且避免二次失真）。
4. 若涉及翻译或跨语言，license 要单独确认（很多数据集禁止再分发衍生内容）。

### P0-7 部署物料有 5 处会直接导致跑不起来的错误

逐条核对过：

| # | 位置 | 问题 | 修法 |
| --- | --- | --- | --- |
| 1 | 24 章快速开始 | `docker exec -i diy-mysql ...`，但 compose 里容器名是 `diy_mysql`（下划线） | 统一命名 |
| 2 | 24 章 | `-p123456`，但 compose / .env 里是 `root123` | 统一为 `root123` 或改成 `$MYSQL_ROOT_PASSWORD` |
| 3 | 33 章 init.sh | 在**宿主机**执行，却连 `mysql`、`rabbitmq`、`minio` 这些**容器内 DNS 名**；且宿主机多半没装 `mysql` 客户端 / `rabbitmqadmin` / `mc` | 全部改成 `docker exec -i diy_mysql mysql ...`、`docker exec diy_rabbitmq rabbitmqadmin ...`，或在 compose 里加一个 `init` 一次性容器 |
| 4 | 22 章目录树 vs 34 章 compose | 目录树写 `deploy/docker/Dockerfile` + `deploy/docker-compose.yml`；compose 却引用 `./deploy/Dockerfile`，且要求"放在项目根目录" | 定死：根目录 `docker-compose.yml` + `deploy/Dockerfile`，目录树同步改 |
| 5 | 34 章 | 挂载 `./deploy/prometheus.yml`，但 22 章目录树里根本没这个文件；`web` 服务的 `./web` 目录也不在目录树里 | 补文件与目录，或删掉该挂载 |

附带两点：

- `version: '3.8'` 在 Compose v2 已废弃，会持续 warning，建议删掉这行。
- `minio` 的 healthcheck 用 `mc ready local`，`local` 这个 alias 不是所有镜像版本都预置，建议改成 `mc ready local || mc admin info local` 或直接用 `curl -f http://localhost:9000/minio/health/live`。
- `.env` 里的 `MYSQL_PWD` 和 compose 里硬编码的 `MYSQL_ROOT_PASSWORD: root123` 是两套配置源，改一个另一个不生效。建议 compose 全部改成 `${MYSQL_ROOT_PASSWORD}` 变量引用。

### P0-8 traceId 没有跨 MQ 传递，"全链路追踪"不成立

**位置**：模块 7、19.4.8、21.1 第 7 条都宣称"traceId 全链路"。

但链路是 HTTP → MQ → Worker，traceId 只在 HTTP middleware 里生成。**跨进程边界不显式传递，链路就断在 MQ 这里**，Worker 日志里是另一个 traceId（或者没有）。这是可观测性最经典的漏点，也是面试官很爱问的"你怎么做到异步链路追踪"。

**改法**：写清楚三段：

1. HTTP 入口生成 `trace_id`，写入 context；
2. 生产者投递时，把 `trace_id` 写进 **AMQP message headers**（同时落 `agent_tasks.trace_id`）；
3. 消费者先读 header 恢复 context，再进业务逻辑；子 Agent 调用透传到 LLM 请求的 `request-id`。

另外指标建议补：`task_e2e_duration` P50/P95/P99、`llm_tokens_total{agent,model}`（成本可视化）、`queue_backlog`（积压告警阈值）。现在只有"QPS/错误率/耗时/堆积量"，粒度偏粗。

## 二、P1：一致性问题（不影响能跑，但一问就露）

### P1-1 状态机与枚举三套写法混用

| 场景 | 文档写法 | SQL 写法 |
| --- | --- | --- |
| 处理中 | `PROCESSING`（12.2） | `running`（agent_tasks.status） |
| 优先级 | `P0/P1/P2`（25.1）、`1高5中10低`（SQL default 5） | 三队列 routing_key `p0/p1/p2` |
| 卡片审核 | `approved/rejected`（SQL status）+ `auto/review`（SQL review_status）+ 三档阈值（13.3） | — |

**改法**：定一份《术语与枚举表》放第二章前，全文强制对齐。建议状态机用 `pending → running → succeeded / failed → dead`（过去分词，跟 SQL 一致），优先级只保留 `P0/P1/P2` 三值（`priority TINYINT` 改存 0/1/2）。

### P1-2 表名单复数混用，正文与 SDD 已经不一致

- 第十章：`users / roles / tutorial_sets / tutorials / cards / agent_tasks`
- 19.5：`user / role / tutorial_set / tutorial / card / agent_task`
- 第二十三章 SQL：复数

**改法**：全文以 SQL 的复数形式为准；19.5 直接引用第二十三章，不要再维护第二份清单。

### P1-3 SDD 章（十九）与前文重复约 90%，且已经开始漂移

19.2~19.10 基本是 1~15 章的复述，占全文约 200 行。**重复必然不一致**（表名单复数已经不一致了）。

**改法**：主文档删掉 SDD 正文，只留一句"SDD 见仓库 `docs/SDD.md`"；把 SDD 拆成独立文件，内容以"决策 + 接口 + 数据模型 + 异常策略"为主，不复述背景。

### P1-4 "优先级队列"与"消息优先级"是两套机制，文档混着讲

- 12.3 写"消息优先级：小批量 > 大批量"；
- 33 章 init.sh 建了 3 个独立队列 P0/P1/P2；
- 30 章坑 6 说"多优先级队列，P0 优先消费"。

但 3 个队列 + `RABBITMQ_CONSUMER_NUM=4` 这一组配置**并不能保证 P0 不被饿死**：如果消费者是"多队列轮询"（`channel.Consume` 多个队列），RabbitMQ 的公平分发会让 P2 的消息照样被取走。要真正做到优先级，得（a）为 P0 预留独立消费者/prefetch，或（b）P2 消费者做主动限速，或（c）改用 `x-max-priority` 单队列 + 优先级消息。

**改法**：明确写成"**P0/P1 各有独立消费者池（各 2 个协程），P2 共享池按 `prefetch=1` 限速；P2 队列堆积超过阈值时暂停拉取**"，这才是能自圆其说的方案。

### P1-5 Agent 级配置化，但配置项只有全局一份

模块 4 和 9.4 都说"每个 Agent 的 Prompt / 模型 / 温度 / max_tokens 可配置"，但 32 章 env 里只有一份 `LLM_MODEL`、`LLM_API_KEY`、`LLM_TIMEOUT`。想给质检 Agent 换更强的模型做不到。

**改法**：Agent 配置落表（`agent_configs(agent_name, model, temperature, max_tokens, prompt_template, enabled)`），env 只留默认值和密钥。顺带这也让"Agent 可插拔/可关闭"真正可运营，而不是改代码。

### P1-6 成本章节（二十七）没有一个数字

标题叫"成本评估"，内容全是定性策略。面试最爱问"这个项目跑一千条要多少钱"，这章目前答不了。

**改法**：补一张估算表（单价按你选的模型填，不必写死）：

| 项 | 计算式 | 示例 |
| --- | --- | --- |
| 单条调用次数 | 6（清洗/材料/工具/步骤/风险/质检） | 6 |
| 单条 token | 输入 ~2k × 6 + 输出 ~500 × 6 ≈ 15k | 15k |
| 千条 token | 15M | 15M |
| 千条成本 | 输入单价 × 12M + 输出单价 × 3M | ___ 元 |
| 降本后 | 缓存命中 20% + 关闭风险 Agent → −35% | ___ 元 |

再补一节"**为什么不做单轮合并**"：如果材料/工具/步骤/风险四路合并成一次调用，成本降到 3 次/条（−50%），但要以实测召回率下降为代价——这个 trade-off 必须量化，否则 27.2 的"批次合并"和第九章"多实体解耦"两个论点互相打脸。

### P1-7 清洗 Agent 物理删除噪声，信息不可回溯

清洗输出是下游唯一的文本输入。如果清洗阶段把某句话误判为"闲聊"删掉，而材料名恰好在那句里，下游全部丢失，且无法定位（原文还在库里，但下游没看）。

**改法**：清洗 Agent 不输出"净化后全文"，而输出**保留段落索引的清洗结果**：

```json
{
  "cleaned_text": "...",
  "removed_spans": [{ "start": 120, "end": 186, "reason": "广告" }],
  "kept_ratio": 0.78
}
```

下游统一拿 `cleaned_text`，但质检/复核页面能一键展开被删片段。这是个小改动，但在面试里是"你考虑过 XX 边界吗"的加分项。

### P1-8 目录结构有三个问题

1. **编排器写了两份**：`internal/service/agent_orchestrator.go` 和 `internal/agent/orchestrator.go` 都叫"编排器"。职责必须二选一——建议 service 层只做"任务→流水线"的用例编排，`internal/agent/orchestrator.go` 负责 Agent 调度与数据流转，service 里的那个删掉或改名为 `pipeline_service.go`。
2. **`internal/pkg/` 位置不对**：`pkg` 惯例是顶层可复用包，放进 `internal/` 就失去"可被外部引用"的意义。要么移到根 `pkg/`，要么改名为 `internal/common/`。
3. **依赖方向有循环风险**：`mq/handlers/agent_pipeline_handler.go` 调 service，而 service 又要投递 MQ（producer）。建议 handler 只调 service 的 `ProcessTask(ctx, taskID)`，producer 通过接口注入，别让 service 直接 import mq 包。

其余小项：`test/` 放集成测试可接受，但单元测试应跟包放 `_test.go`；软删除只有 `users`/`tutorial_sets` 有 `deleted_at`，`tutorials`/`cards` 没有，而验收标准写"软删除规范"——补齐或改口径。

### P1-9 接口清单有 5 处遗漏 / 权限过宽

| 问题 | 说明 |
| --- | --- |
| 缺 `POST /auth/refresh` | 但阶段 1 验收明确要求"刷新 token" |
| 缺 `GET /tasks` | 前端任务列表页没接口 |
| 缺 `GET /cards?review_status=pending` | 或独立的复核队列接口，否则复核员无法"领取待办" |
| 缺 `PUT /cards/{id}` | 目标用户写"查看/编辑卡片"，但只有 review 接口 |
| `GET /cards/export` 权限 = 普通成员 | 全量导出应限管理员或限教程集范围；且大数据量导出应走异步任务 + 下载票据 |

另外统一响应体外层只有 `code/msg/data/traceId`，但全文提到"错误码体系"却**没有一张错误码表**，也没有分页响应结构（`list/total/page/page_size`）。

### P1-10 安全细节偏薄

- **JWT 存储与刷新完全没定义**：access/refresh 各自 TTL、刷新是否轮换、登出是否拉黑（这正是 Redis 该出现的场景，19.3.3 却把"JWT"含糊地挂在 Redis 上）。建议明确写：access 15min 无状态 + refresh 7d 存 Redis 白名单，登出删白名单。
- **CSRF**：如果 token 放 header，CSRF 风险很低；如果放 cookie，就必须写 SameSite + CSRF token。文档写"XSS/CSRF 防护"但没说前提，属于凑词。
- **非 root 运行**从"可选优化"提到"必须"——这是容器安全的基本项，写成可选反而显得不专业。
- `operation_logs` 表有，但**没有定义哪些操作写审计**（建议：导入、删除、重试、复核、权限变更、导出六个动作）。

### P1-11 验收标准里有一条指标是无效的

21.4 第 2 条："步骤时序正确率 ≥ 90%（**质检复核后**）"——复核后的人工修正结果当然接近 100%，这个指标不衡量系统能力。

**改法**：拆成两个：

- 自动通过样本（confidence ≥ 0.8）的步骤时序准确率 ≥ 90%（**未经人工修改**）；
- 复核员对步骤的修改率 ≤ 15%。

再加一组**压测与故障演练验收**（现在只有"简单压测"一句）：

- 1000 条批量任务端到端 P95 ≤ ___ 分钟（先算出来再填）；
- 杀掉 1 个消费者实例，任务全部完成无重复扣费；
- LLM 接口 100% 超时 5 分钟，系统不雪崩、任务进死信、恢复后手动重试成功。

## 四、路线图的一个现实问题

第十六章合计 12 周（阶段 9 并行仍要 12 周）+ 每阶段都是生产级验收。对一个"边上班边准备面试"的项目，**大概率死在阶段 4 之前**（因为阶段 1-3 全是后端地基，看不到任何 Agent 效果，正反馈极慢）。

建议改成两段式：

**MVP 切片（4 周，可面试）**
1. 周 1：单条教程跑通 清洗→材料/工具/步骤→质检，卡片存 MySQL，用一个最小 HTTP 接口触发（不要 MQ、不要 RBAC、不要 MinIO）。
2. 周 2：卡片 JSON 渲染 + 复核页面（前端价值最高的一屏）+ 20 条手工标注的效果报告。
3. 周 3：补 MQ 异步 + 幂等 + 重试（此时你已经有一个能跑的东西，异步是"补强"不是"从零")。
4. 周 4：Docker Compose 一键起 + README + 面试话术。

**增强（有时间再做）**：RBAC、MinIO、Prometheus/Grafana、优先级队列、cost 报表。

理由：面试官关心的是"你怎么把 LLM 的不确定性工程化"，不是"你有没有 Grafana 大盘"。先让流水线跑出卡片，再去补地基，正反馈会救你。

## 六、可以直接写进面试话术的三句"防御性表述"

改完之后，这三句能让追问变成加分：

1. **"置信度不是模型说的，是模型给证据、代码算分。阈值 0.8 是在 200 条标注样本上按 precision-priority 定的。"**
2. **"清洗不物理删除，只标记 span，下游拿清洗文本，复核页能展开被删片段——防止清洗阶段误删材料导致不可逆信息丢失。"**
3. **"我做了单轮 baseline 对照：同样 200 条，多 Agent 的字段召回从 X% 提到 Y%，token 成本是 Z 倍，所以只在置信度分流能省下人工的场景下，这个成本是划算的。"**
