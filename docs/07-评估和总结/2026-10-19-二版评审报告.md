## 二、新发现的 P0（4 项）

### P0-1 初始化数据把 `TODO` 当 Prompt 存进去，系统跑起来第一句就废

`03-data-design.md:268-273` 的初始化 SQL：

```sql
('clean', 'deepseek-chat', 0.10, 1500, 'TODO: 见 docs/prompts/clean.md', 1),
...
('quality', 'deepseek-chat', 0.00, 1500, 'TODO: 见 docs/prompts/quality.md', 1),
```

而 `docs/prompts/` 下只有 `material.md` 和 `quality.md` 两个文件，**`clean.md` / `tool.md` / `step.md` / `risk.md` 四个 Prompt 根本不存在**。

后果不是"文档少一篇"，是**照着这份 SQL 初始化完，六个 Agent 有四个会把 `TODO: 见 docs/prompts/clean.md` 这句中文当 Prompt 发给 LLM**。冒烟测试第一步就会挂，而且报错信息会非常难懂（JSON 解析失败，而不是"Prompt 没配"）。

顺带两个连带问题：
- `prompts/material.md:5` 和 `prompts/quality.md:86` 都写"Prompt 放在 `server/docs/prompts/`"，实际在 `docs/prompts/`，路径两套。
- `agent_configs.prompt_template` 是 `MEDIUMTEXT NOT NULL`，用"文件路径"当 Prompt 内容是错的设计：**要么把 Prompt 正文写进表（可运营改），要么表里只存版本号/文件 key，由代码加载文件**。现在的写法两头不靠——改 Prompt 要改 SQL，改文件又不生效。

**改法**：
1. 补 4 个 Prompt（照着 `quality.md` 的结构，每个 30 行就够）；
2. SQL 里 `prompt_template` 改成 `'builtin:clean@v1'` 这种版本标识，代码按标识从 `docs/prompts/` 加载，DB 里存的是"当前生效版本"；
3. 启动时做一次自检：`agent_name` 对应的 Prompt 加载不到 → 直接 fail fast 并打印是哪个 Agent，别等第一个任务跑挂。

> 这条优先级最高。文档再漂亮，demo 跑不起来就全废。

## 三、P1（影响专业度，一问就露）

### P1-1 接口设计只有"清单"，没有"契约"

`04-interface-design.md` 全文 75 行，是 10 份文档里最薄的一份（其他 200–400 行），但它恰恰是**后端开工的第一手依据**。现在缺：

- 19 个接口**没有一条 request / response body**。`POST /tasks` 传什么？`{set_id, priority, agent_switches}` 还是 `{tutorial_ids[]}`？批量粒度是"整个教程集"还是"选中的若干条"？决定 `agent_tasks` 是 1 条还是 N 条，进而决定进度怎么算——**这个不定，P0-2 修的表结构还是用不对**；
- **无字段校验规则**（长度、枚举、必填）；
- **无幂等重复提交语义**：`04:57` 错误码表写"409 幂等键重复提交（**返回已有任务**）"。409 和"返回已有任务"是互斥的——要么 409 + body 带 task_id，要么 200 + 已有资源。选一个，写清楚；
- **无导出链路**：`04:28` 写"异步任务 + 下载票据"，但没有任何查票据 / 下载文件的接口，也没有票据表；
- **无 OpenAPI / Swagger 定义**（正文说"Swagger 自动生成"，但没给 spec）。

**改法**：至少把 `POST /tasks`、`GET /tasks/{id}`、`PUT /cards/{id}/review` 三个接口写成完整契约（请求体 + 响应体 + 错误码 + 幂等语义），其余给一张"字段表"即可。

### P1-2 两条路由在 Gin 里会打架

`04:24` `GET /api/v1/cards/review-queue` 与 `04:25` `GET /api/v1/cards/{id}`——同一路径段既是静态又是通配。Gin 的路由树对这类"静态段 + `:param` 兄弟节点"历史上是 **panic: conflicts with existing wildcard**，具体行为随版本变化，需要在目标版本上实测。

**改法**（零成本，别赌）：复核队列改成独立前缀 `GET /api/v1/review-queue`，或 `GET /api/v1/cards/-/review-queue`。同时 `cards/review-queue` 这种命名在 REST 里本来就不该挂在资源 ID 的兄弟位置。

### P1-3 审计字段与表结构对不上，落库必缺字段

`07 §7.4.2` 定义审计字段：`operator_id / action / target_type / target_id / detail / ip / created_at`。
`03` 的 `operation_logs` 表（`:248-258`）实际是：`user_id / action / target / ip / detail / created_at`。

差三个：`operator_id`↔`user_id` 命名不同，**`target_type` 整列不存在**，`target_id` 被拍平成一个 `target VARCHAR(128)`。

按 07 的代码写，SQL 直接报 `Unknown column 'target_type'`。

**改法**：以表为准改 07（`user_id / action / target_type / target_id / ip / detail`），并给 `operation_logs` 加 `target_type` + `target_id` 两列。

### P1-4 置信度扣分规则：没有基数，没有下限，会算出负数

三处口径：

- `05:294-299`：四维度权重 **40% / 25% / 25% / 10%**，`confidence = Σ(维度得分 × 权重)`；
- `prompts/quality.md:77-80`：字段完整性 **每项扣 10 分**、时序 **每对扣 8 分**、一致性 **每个扣 5 分**；
- `05:126-131` 示例 `confidence_detail` 各维度是 **0~1 的小数**（0.90 / 0.80 / 0.85 / 0.95）。

矛盾在于：**扣 10 分是从 100 里扣，还是从该维度的满分（40）里扣？** 若从 100 里扣，扣 4 个缺失字段 = −40，已经吃掉整条 40% 权重，其余维度再扣就变负；若从维度满分扣，"每项扣 10 分（满分 40）"只能容纳 4 个问题，第 5 个就负了。**没有封顶（clamp 到 0）、没有归一化说明。**

**改法**：写成公式，别写"扣 X 分"：
```
completeness = max(0, 1 − 0.25 × missing_count)        # 缺失 4 项归零
temporal     = max(0, 1 − 0.20 × conflict_pairs)       # 冲突 5 对归零
grounding    = hit_entities / total_entities
text_quality = 规则分（0~1）
confidence   = 0.4×completeness + 0.25×temporal + 0.25×grounding + 0.10×text_quality
```
再给一个"3 个缺失字段 + 2 对冲突"的算例，把 0.86 这个示例值反推出来对上。

### P1-5 `quality_flags` 没有生产者

`05:132` 卡片示例有 `quality_flags: ["tool_missing:砂纸"]`，`05:143` 说"质检发现的问题标记数组，前端标黄展示"。

但质检 Agent 的输出（`prompts/quality.md:17-38`）是 `missing_fields / step_conflicts / grounding_issues` **三个结构化数组**，**没有任何一步生成 `quality_flags` 这个字符串数组**。中间缺一个映射层，而且映射层属于"代码算分"那一层，文档里没写。

**改法**：在 05 §10.2 加一行映射规则：`missing_fields[] → "missing:{field}"`、`step_conflicts[] → "conflict:{seq_a}-{seq_b}"`、`grounding_issues[] → "ungrounded:{entity_name}"`，由打分函数一并产出。

### P1-6 `removed_spans` 用字符偏移，实现时大概率对不上

`05:56-63` 的设计很好（不物理删、可回溯），但字段是 `{start: 120, end: 186, reason, text}`——**字符偏移由 LLM 输出**。

LLM 数不准字符位置，这是众所周知的事实。实际跑起来 `start/end` 会大面积错位，复核页"一键展开被删片段"就会展开到一句毫不相干的广告或正文。

**改法**（保留设计、换实现）：
1. LLM 只输出 `{reason, text}`（被删的那句原文），**不输出偏移**；
2. 后端在 `cleaned_text` 或 `raw_text` 里做**唯一子串定位**（`strings.Index`），命中则补 `start/end`，未命中/多处命中则丢弃该 span 并记一条 warning；
3. 落库时校验 `raw_text[start:end] == text`，不等即视为无效 span。

这是一个"面试官问'你怎么保证偏移对'时能不能答上来"的点，现在文档把偏移当既定事实。

### P1-7 软删除口径仍未统一

`07:53` 写"users、tutorial_sets 有 `deleted_at`"（对），但 `10:242` 验收项写"**软删除规范**"，而 `03` 的 `tutorials` / `cards` / `agent_tasks` 全都没有 `deleted_at`。上一版 P1-8 的尾项没清。

**改法**：二选一并写进 03 的设计要点——(a) 给 `tutorials` / `cards` 补 `deleted_at`；(b) 明确"只对聚合根（user / tutorial_set）软删，子表随父级级联隐藏，不单独软删"，然后把 10:242 的验收项改精确。

### P1-8 License 只登记，没落地约束

`05:334-336` 列了 license（CC BY-NC-SA、非商业研究用途），这是难得的诚实。但**没有一句说明这些约束对平台意味着什么**：

- CC BY-NC-SA 的 **NC** 意味着基于它的产出**不能商用**；**SA** 意味着衍生作品要同协议开放；
- Instructables "非商业研究用途"意味着**抓取入库 + 再分发给内容平台**本身就有风险；
- 而项目定位是"面向 UGC 内容平台"，天然带商用属性。

**改法**：在 05 §15 加 3 行"合规边界"：公开集仅用于效果评测不出库、商用样本只用自建集、产出卡片标注来源与 license 字段（正好 `tutorials` 表该加一个 `license` 列）。这条写清楚，是加分项；不写，被问到时是减分项。

### P1-9 占位符没清零（这条最伤）

| 位置 | 内容 |
| --- | --- |
| `10:32` | "字段召回率从 **X%** 提升到 **Y%**"——直接写在面试话术里 |
| `10:264` | "1000 条批量任务端到端 P95 ≤ **___** 分钟" |
| `10:325-326` | "千条成本（输入/输出）… 约 **___** 元" |
| `10:341` | 面试话术："成本约 **___** 元（填实测值）" |
| `baseline.md:36-47` | B.4 全是 `~75%` `~88%` 的**预期值**，标题自己写着"写进 README 时替换为实测值" |

`baseline.md` 的预期值本身没问题——问题是它被 `10:48`、`10:199`、`21.4` 当成了"已经做过实验"的证据在用。**一旦面试官问"你这个 88% 是怎么测的"，回答"还没测"，前面所有数字的可信度会一起塌。**

**改法**：建一张"待填实测值"清单（放在 `10` 或 baseline 顶部），每项标 `TBD` + 预期完成周次；**面试前必须清零，清不了的从话术里删掉，不要留 `X%`**。删掉一个数字，比留一个 `X%` 安全十倍。
