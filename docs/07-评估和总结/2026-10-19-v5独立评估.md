# v5 独立评估（第三方重审）

> 评审对象：`docs/` 下 01–11 + `baseline.md` + `prompts/`（3 287 行正文 + 437 行 Prompt）
> 评审标准：`评分标准.md`（10 维度 × 100，含 4 条硬性否决）
> 评审方式：**不采信 v4 的 94 分结论**，从零取证；每条扣分给"位置 + 现象 + 判据"，可逐条复核。
> 日期：2026-10-19

---

## 一、结论先说

**v4 的 94 分（A 级）不成立。按同一把尺子重审，当前文档是 83 分（B 档），5 处 P0。**

比分数更重要的是**复发规律**：

> v4 修了 17 处，字段类的都修住了，**机制类的又漂回去了**。
> v4 的 5 个 P0 里，有 3 个（字段无落点、熔断终态自相矛盾、把未做的实验写成已做）以**变体形式**重新出现在别的文件里——同一种病，换了个位置。

这也是本轮 83 分与 v4 修改前的 82 分几乎相同的原因：不是文档没进步，而是**这轮新增的修订没有覆盖"同一事实的其他副本"**。

---

## 二、评分口径声明（为了让分可复现）

1. **硬性否决只对"契约级事实"生效**：字段名、路径、枚举、状态机、机制参数、实验结论。
   叙事级摘要（如 1.4 的角色权限表写错一格）计为一致性问题并扣分，**不触发否决**。
   理由：若按字面执行"同一事实两处不同即否决"，v1 以来每一版都会被判死，尺子就失去区分度。
2. 每条扣分必须可核对（位置 + 现象 + 判据），否则不计。
3. 单维度取整，综合分取算术平均，与 `评分标准.md` 一致。

## 三、5 处 P0（交付前必须改）

### P0-1 `difficulty.reason` 全链路有承诺、无落点

| 环节 | 承诺 |
| --- | --- |
| `05:134-137` Card Schema | `"difficulty": { "level": "easy", "reason": "步骤 5 步以内…" }` |
| `prompts/risk.md:38` | 输出 `difficulty.reason` |
| `prompts/risk.md:72` | `reason` 为空要"降置信度"——说明它是被消费的字段 |
| `04:181` 复核接口 | 请求体里带 `difficulty: {level, reason}` |

**现实**：`03:130` 只有 `difficulty VARCHAR(16)`；`05:176` 的 Go struct 只有 `Difficulty string`；`3.1` 表清单同样只有 `difficulty`。
**三段承诺，零个存储位置。**

后果：复核员改了难度理由，落库即丢；`GET /cards/{id}` 返回的 Card Schema 里 `reason` 永远为空。这正是 v4 的 P0-1（`confidence_detail` 无落点）的同款，只是换了个字段。

**判据**：D3-5 模型一致归零 → 命中否决项 3（同一字段两处不一致）。
**改法**：`cards` 增 `difficulty_reason VARCHAR(255)`，或把 `difficulty` 整体改成 `difficulty_json`（推荐后者，和 `risk_json` 同构）。

### P0-2 熔断后任务是什么状态，两处答案仍然相反

- `06:30` 降级：熔断期间**任务保持 `pending`、不空转不失败，窗口结束自动续跑**
- `08:64` 降级矩阵：LLM 整体不可用 → 熔断 60s，**任务保持 `pending`**，恢复后自动续跑
- `10:270` 演练验收：LLM 100% 超时 5 分钟 → **任务进死信；恢复后手动重试成功**

前两处是"可恢复态"，第三处是"终态 + 人工介入"，行为完全相反。v4 的 P0-3 只改了 06 与 08，**10.6.5 是同一事实的第三个副本，没跟着改**。

后果：验收用例与设计承诺对不上——按 06/08 实现，演练第 3 项永远"不通过"；按 10 实现，8.2.1 的"不丢任务"就成了空话。

**判据**：否决项 3；D5-3/D5-4。
**改法**：`10.6.5` 第 3 行改成"平台不雪崩、任务保持 pending，窗口结束后自动续跑；死信只承接单条重试超限"，并把"手动重试"删除。

### P0-5 置信度 < 0.5 的卡片被标成 `rejected`，却进不了复核队列

- `05:323`：`confidence < 0.5` → `review_status = rejected`，"要求人工确认或重跑"
- `04:54`：`GET /review-queue` 只查 **`review_status = pending_review`**
- `05:327`：复核闭环承诺"低置信样本进复核"

`< 0.5` 的卡片既不在复核队列里，也不是正常入库状态，**没有任何界面能捞到它们**。而且 `rejected` 同时被 4.3.4 用来表示"人工拒绝"，两种语义共用一个枚举值——`Q5 复核修改率`的分母（"进复核的卡片"）因此无法界定。

**判据**：D5-4（状态无入边/无出口）+ D4-1（功能页无对应接口）；机制不闭环，按 P0 处理。
**改法**：三选一并全文统一——① 新增 `auto_rejected` 状态并纳入队列；② `< 0.5` 也落 `pending_review`，用 `confidence` 排序分层；③ 明确 `< 0.5` 直接丢弃并写"不可复核"说明。推荐 ②，改动最小。

## 七、v4 为什么会漏这三类问题

v4 的方法论是"**同一事实去全库搜它出现了几次、取值是否一致**"。这一招很有效，但它只覆盖了三类问题中的第一类：

| 检查类型 | v4 是否做 | 典型漏项 |
| --- | --- | --- |
| ① 抄写一致性（同一事实多处取值是否相同） | ✅ 做了，且做得很好 | —— |
| ② **落点检查**（这个字段 DDL / struct 能不能接住） | ❌ 没做 | `difficulty.reason`、`ToolItem.spec` |
| ③ **可算性检查**（这个数字能不能用给定参数算出来） | ❌ 没做 | P5 吞吐 × `LLM_MAX_CONCURRENT=5` |
| ④ **入边检查**（谁能把这个状态置成这个值） | ❌ 没做 | `<0.5 → rejected` 无出口、`failed` 无入边 |

> 一句话：**v4 查的是"抄得对不对"，v5 查的是"跑不跑得起来"。**
> 前者的敌人是复制粘贴，后者的敌人是"每句话都对，合起来不成立"。

## 九、一句话

**这一版的问题不是"写得差"，而是"改了一半"：v4 修的字段类问题都守住了，机制类问题在别的章节原样存活。**
真正的验收标准不是"全文 grep 不到冲突"，而是"按这份文档建表、写代码、起容器，第一次能不能不报错"。
