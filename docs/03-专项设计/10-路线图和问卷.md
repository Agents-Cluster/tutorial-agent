> 本文档包含：面试亮点、开发路线图、交付物清单、避坑点、验收标准、并发控制、成本评估、可扩展设计、已知缺陷、踩坑记录。

## 10.1 面试亮点与工程痛点清单

### 10.1.1 平台独有的 4 大亮点

1. **噪声治理 + 多实体解耦**：清洗 Agent 先净化，材料/工具/步骤/风险各自独立 Agent，单轮 LLM 被噪声干扰、漏项错乱的问题被系统化缓解；
2. **LLM 出证据、代码算分**：置信度不是模型拍脑袋给的，是模型输出证据、程序按权重算的，可复现、可回归；
3. **异步任务编排 + 子任务独立重试**：Agent 环节失败只重试该环节，不整条重跑，省 token 且稳定；
4. **通用可迁移架构**：场景是载体，流水线是资产，换 Prompt 与字段定义即可迁移到菜谱、科普、课程等任意 UGC 文本结构化场景。

### 10.1.2 面试可讲的坑（提前准备，含答案方向）

| 坑 | 怎么讲 |
| --- | --- |
| 教程文本夹杂大量广告闲聊 | 清洗 Agent 独立剥离噪声，净化后再抽取；removed_spans 可回溯 |
| LLM 输出 JSON 解析失败 | 三层兜底：Prompt 约束 + 解析重试 + 质检标记人工复核 |
| 步骤顺序被拆乱 | 步骤 Agent 专职 + 质检时序冲突对 + 低置信人工复核 |
| 批量导入任务堆积 | P0/P1/P2 独立消费者池 + 队列监控告警 + 消费者水平扩展 |
| LLM 接口不稳定 | 熔断 + 指数退避重试 + Agent 子任务独立状态 |
| 数据集脏数据多 | 离线预处理分层抽样 + 在线导入校验 + 坏样本集专门测兜底 |
| 清洗误删材料导致信息丢失 | removed_spans 设计，复核页可展开被删片段，下游仍拿清洗文本 |

### 10.1.3 高频面试追问及速答

**Q1：为什么不用单轮 LLM 一次性输出，要做多 Agent？**

> UGC 文本噪声多，一次性提取多种实体容易互相干扰。拆分独立 Agent，先做文本净化，再分别提取材料、工具、步骤、风险，任务解耦。单个子任务出错只需重试该 Agent，不用重新处理全文，提升稳定性、降低 token 消耗。
>
> 我设计了单轮 baseline 对照（协议见 baseline.md：同 200 条样本、同模型、同温度、盲评、失败样本计入分母），**尚未跑**，结果待登 11.2-R4。**token 成本约 5 倍**是设计推导（见 11.3：单条 15k vs 3k），实测待 11.2-R6 登记；召回率提升幅度同样以 11.2 实测为准——没测出来之前，我不会说具体百分点。这个 trade-off 只在"人工复核成本高"的场景成立。

**Q2：怎么处理 LLM 输出 JSON 不稳定的问题？**

> 三层兜底：第一，Prompt 强制指定 JSON schema；第二，后端捕获 JSON 解析异常，解析失败的任务自动重试；第三，质检 Agent 校验字段合法性，异常样本进入人工复核。

**Q3：置信度是怎么算的？为什么不让 LLM 直接给分？**

> LLM 直接给分不可靠——同一份输入两次调用可能给 0.82 和 0.61，阈值分流就失效了。我的方案是"LLM 出证据、代码算分"：LLM 输出缺失字段列表、步骤冲突对、不一致片段，代码按四个维度加权算分。这样分数可复现、可调试、改了 Prompt 能量化效果变化。0.8 这个阈值**目前是设计值、还没标定完**：标定方法是在 200 条人工标注集上画 precision-recall 曲线取拐点，结果按 11.2 的 R5 行登记；没登记之前，我说的是"待验证的阈值"，不说"调好的参数"。

**Q4：Agent 之间怎么通信？为什么不让它们自由对话？**

> 所有 Agent 通过编排器中转，不直接对话。自由对话不可控、易发散、难观测；编排器中转保证每步输入输出可记录、可重试、可审计。

**Q5：这个平台怎么评估效果？**

> 固定样本集统计：字段召回率（材料/工具/步骤是否齐全）、步骤时序正确率、JSON 解析失败率、高置信自动通过率。对照实验的协议已定稿（`baseline.md`：同 200 条、同模型、同温度、盲评、Kappa ≥ 0.75、失败样本计入分母），**结果按 11.2 的 R1–R4 登记**。在结果落表之前，我不说"提升了多少"——先承诺"什么结果算不成立"（+10pp 以下就承认多 Agent 不划算），再看数据。

**Q6：教程本身是错的怎么办？**

> 平台边界是忠实结构化提取原文内容，不校验教程实操正确性；质检只校验抽取结果与原文一致。实操安全校验超出平台范围，在文档中明确声明。

**Q7：MQ 投递失败怎么办？写库成功但 MQ 挂了？**

> 本地消息表 outbox：写 MySQL 和写 outbox 在同一个事务里，后台协程扫 outbox 投 MQ，投成功标记 sent，消费者 ACK 后标 confirmed。再加兜底定时任务，扫超时的 pending 记录重新投递。这是标准的 transactional outbox pattern。

### 10.2.6 排期优化说明

原来的"两段式"把 RBAC、MinIO、监控都放到了第二阶段，相当于砍需求。现在全量排进 4 周，靠三个手段挤出时间：

1. **前后端并行**：前端不等后端 API，先用 Mock 数据画 UI，后端好了再对接。每天后端 6 小时 + 前端 2 小时，不浪费等待时间。
2. **组件按需引入**：不是第一天就把 MySQL/Redis/MQ/MinIO 全搭好，而是用到哪个搭哪个。第 1 周只用 MySQL+Redis，第 3 周才加 RabbitMQ，第 4 周才加 MinIO。
3. **Agent 开发提速**：6 个 Agent 结构完全一样（统一接口 + Prompt + 解析），写完第 1 个，后面 5 个都是复制改 Prompt，速度会越来越快。

> **风险提醒**：4 周全量排期比较紧，优先级是：核心流水线 > 前端核心页面 > 异步任务 > RBAC/MinIO/监控。如果时间不够，最后一天的监控和统计页可以往后放，但核心的多 Agent 流水线必须做扎实。

## 10.4 避坑点

1. ❌ 不要简化成"单轮 LLM + 存 JSON"——缺了多 Agent 编排与质检，只能算 prompt 工程；
2. ❌ 不要 Controller 直接写 SQL、不分层；
3. ❌ 不要硬编码密钥、数据库地址、API Key（必须走环境变量）；
4. ❌ 不要忽略全局异常处理，接口随意 panic；
5. ❌ 不要不写任何测试；
6. ❌ 不要花大量时间调大模型回答效果——平台核心是多 Agent 工程架构，不是 prompt 调优；
7. ❌ 不要一上来就堆进阶功能（向量库、相似推荐）——先跑通主线流水线；
8. ❌ 不要把全部样本无差别送 LLM——先做离线过滤，坏样本不进流水线，控制成本；
9. ❌ 不要让 LLM 直接给置信度分数——不可复现、不可校准，改成"LLM 出证据、代码算分"；
10. ❌ 不要跳过 MVP 直接上全量架构——先跑通单条流水线，再补 MQ/RBAC/MinIO。

## 10.5 阶段验收标准

> MVP 阶段（前 4 周）验收标准简化，聚焦"能不能跑通流水线"。

### 10.5.3 MVP-3：MQ 异步 + 幂等（第 3 周末）

| 3 | LLM 100% 超时 5 分钟 | 平台不雪崩：连续失败达阈值触发熔断后，任务保持 `pending`、不空转，窗口结束自动续跑（接管时序见 6.2）；熔断**前**已耗尽重试进入死信的子任务，经 4.3.3 人工重试恢复 |
| 4 | MQ 停机 10 分钟 | outbox 持续积压；恢复后 5 分钟内全部消费完 |
| 5 | MySQL 主库重启 | 健康检查 30s 内转 503，恢复后任务不丢（API 前无做健康摘流的 LB，前端 nginx 只把 503 原样透传；"摘除/挂回"由外部探活执行，见 8.2.1 与 9.12.3） |

## 10.7 并发与资源控制策略

> **阈值（消费者数、单用户并发、信号量、积压告警线）的唯一权威在 6.5**，本节只讲"为什么这么设计"，不重复数字。

### 10.7.1 为什么是"多队列 + 独立消费者池"，而不是"单队列 + 消息优先级"

RabbitMQ 的 `x-max-priority` 只在**同一个队列内**排序，而消费端是并发拉取的：只要 P2 的消息先被 push 到某个空闲消费者，它就会先跑。也就是说，单队列 + 优先级只保证"排队顺序"，不保证"不被低优任务占住消费者"。

真正要解决"大批量任务饿死小任务"，必须做**资源隔离**：P0/P1 各有专属协程，P2 只能用自己的那一个——这是 6.5 那张表的设计依据。

代价：队列数 × 消费者数增加，运维要盯 3 个队列的积压；收益是 P0 的最坏等待时间从"队尾"变成"自己队列的队尾"。

### 10.7.2 LLM 侧的并发不能只靠消费者数

消费者数是"任务级"并发，LLM 调用是"请求级"并发：一个任务一次只处理一条教程，但四路并行会让单任务瞬间发起 4 个 LLM 请求。所以还需要一层**全局信号量**兜底，否则 4 个消费者 × 4 路并行 = 16 个并发请求，直接触发上游限流。

三层限流的关系：

| 层 | 控制什么 | 在哪 |
| --- | --- | --- |
| 接口层 | 用户/ IP 的提交速率 | 中间件 |
| 任务层 | 同时运行的教程条数 | 消费者数（6.5） |
| 请求层 | 同时进行的 LLM 调用数 | 全局信号量 |

> 三层缺一层，就会出现"接口限了、任务限了，LLM 还是被打爆"或者"LLM 有余量、任务却排不上"的错配。

## 10.8 可扩展设计

1. **Agent 插件化设计**：Agent 统一接口（Name/Run），新增 Agent（难度校准、用料量化）只需实现接口并注册，编排器无需改动；
2. **场景迁移能力**：更换 Agent 的 Prompt 与字段定义，即可迁移到菜谱、科普、线上课程等 UGC 内容结构化场景（面试核心卖点）；
3. **存储层抽象**：对象存储抽象接口，可替换为阿里云 OSS；
4. **消息抽象**：MQ 抽象接口，可切换为 Redis MQ；
5. **可降级**：任一 Agent 可独立关闭，降级后卡片缺字段并降置信度，主流程不断；
6. **Agent 配置运营化**：模型/温度/Prompt 落 `agent_configs` 表，改配置不用发版。

## 10.9 模型调用成本评估与降本策略

### 10.9.1 成本构成

| 成本项 | 用途 | 量级 |
| --- | --- | --- |
| LLM 文本调用 | 各 Agent 拆解/清洗/质检 | 主要开销，按 token 计费 |
| Embedding | 扩展阶段相似推荐（MVP 不做） | 极低 |

### 10.9.2 成本估算（推导过程，目标值见 11.1.4 的 C1–C4）

| 项 | 计算式 | 示例值 |
| --- | --- | --- |
| 单条调用次数 | 6（清洗/材料/工具/步骤/风险/质检） | 6 次 |
| 单条输入 token | ~2000 × 6 ≈ 12000 | 12k |
| 单条输出 token | ~500 × 6 ≈ 3000 | 3k |
| 单条总 token | ~15k | 15k |
| **千条 token 消耗** | 15k × 1000 | **15M tokens** |
| 千条成本 | `12 × P_in + 3 × P_out`（元） | P 为"每百万 token 单价"，代入 11.3.1 计算式 |
| 降本后（缓存 20% + 关闭风险 Agent） | 约为原成本的 65%（C4） | 按 11.3.1 的系数重算 |

> `P_in` / `P_out` 是**变量**，不在这里写死：模型定价会变，写死就意味着过期。
> 计算与代入方法见 **11.3 成本计算模板**（计算式 + 降本系数表），实测 token 用量登记在 11.2 的 R6 行。
> 重点是：**你能把账算出来，而不是只说"成本可控"。**

### 10.9.3 降本策略（面试必讲）

1. **离线过滤前置**：空文本、超短/超长文本在导入时拦截，不进流水线；
2. **置信度分流**：高置信样本直接入库、低置信进复核（5.4.4），人工成本只花在低置信样本上——置信度是质检的**产物**而非开关，分流不减少调用次数；
3. **缓存**：同一原文重复任务命中缓存结果，不重复调用 LLM；
4. **子任务独立重试**：失败只重跑失败 Agent，不整条重跑；
5. **Agent 开关**：风险评估等可选 Agent 可关闭；
6. **批次合并的 trade-off**：材料/工具/步骤/风险四路合并成一次调用，成本降到 3 次/条（-50%），但实测召回率会下降——这个 trade-off 要量化后写进 README。MVP 阶段保持 6 次独立调用，优先保证质量。
7. **用量监控**：按教程集统计月度 token 消耗（11.3 口径），接近阈值时告警让运营介入；MVP 不做自动暂停——库里没有配额实体，硬做就是无手段承诺（见 10.11）。

> 面试话术：**平台定位轻量化，所有模型走第三方 API 不本地部署；成本大头是 LLM 文本调用，千条教程约消耗 15M tokens，成本 = 12×P_in + 3×P_out 元（P 为每百万 token 单价，代官网价即得）。降本靠离线过滤、置信度分流、缓存、子任务独立重试四件事，实测 token 用量登记在 11.2。**

## 10.10 项目权衡与取舍

> 面试必讲：讲清楚你**主动做的取舍**，而不是"没想到"。

1. **不本地部署大模型**：降低部署复杂度与硬件门槛；代价是依赖第三方 API 的网络与成本风险。应对：熔断、重试、用量统计、并发控制；
2. **MVP 不做向量库与相似推荐**：降低组件数量，优先验证 Agent 流水线；代价是没有内容推荐能力，可后续迭代；
3. **Agent 不自由对话，全部经编排器中转**：可控、可观测、可审计；代价是丢失多 Agent 自由协商的灵活性（本场景不需要）；
4. **不校验教程实操正确性**：平台只结构化提取原文内容，实操安全校验超出范围，边界清晰、合规风险低；
5. **不做消息事务**：采用 outbox 本地消息表 + 消费幂等保证最终一致性；代价是最终一致性而非强一致性，适合文本处理这类允许秒级延迟的业务；
6. **LLM 不直接给置信度分数**：改成"LLM 出证据、代码算分"，牺牲一点灵活性换可复现、可回归；
7. **MVP 先跑通流水线再补地基**：先 4 周出可面试的 demo，再补 MQ/RBAC/MinIO/可观测；代价是前期架构不够"完整"，但正反馈快、不会半途而废。

> 面试话术：**没有盲目上复杂中间件，基于业务规模做技术选型，避免过度设计。**

## 10.11 已知缺陷与待优化点

> 真实平台必备，不要写"完美无缺"。

1. 质检置信度的四维权重与阈值 0.8 **目前是人工设定，尚未标定**（标定协议见 11.1.3、baseline.md，结果待登记 11.2 的 R5 行）；即使标定完成，200 条样本量仍偏小，结论外推有风险；
2. 步骤时序校验依赖 LLM 输出冲突对，复杂流程教程可能误判；
3. 材料规格归一化（"一点点胶水"→定量）未实现，依赖人工复核；
4. 无告警推送（钉钉/企业微信 webhook），仅 Grafana 大盘查看；
5. Agent Prompt 调优依赖人工，未做自动评估回归；
6. 材料/工具 name_norm 归一化用的是同义词表 + 简单规则，未做重量级 NLP；
7. 无任务级月度 token 配额与自动暂停，只有统计与告警（10.9.3 第 7 条已按此收敛为用量监控）；
8. **5.4.2 的 `quality` 子项阈值与惩罚项常量是"可实现的初值"，不是标定结果**：800 字长度下限、连续 ≥3 个噪声符号、非教程句词表，以及 0.10/0.05/0.05×n 三个惩罚常量，都需要在 R1–R9 实测时与置信度分布一起校准；改这些常量等于改分数，必须在 11.4.1 留痕。

## 10.12 项目踩坑记录

> 面试口述的坑，全部写进文档，证明你真实踩过。

1. **坑 1：教程夹杂大量广告与闲聊，抽取结果被带偏**

根因：未净化直接抽取，模型把广告内容当教程内容。

解决方案：清洗 Agent 前置剥离噪声，再进入材料/工具/步骤抽取。removed_spans 记录被删片段，可回溯。

2. **坑 2：步骤顺序被拆乱，先上漆再切割**

根因：长文一次提取多实体，步骤识别不专注。

解决方案：步骤拆解 Agent 专职处理 + 质检 Agent 输出时序冲突对 + 低置信人工复核。

3. **坑 3：LLM 输出的 JSON 频繁解析失败**

根因：Prompt 未强约束格式。

解决方案：指定 JSON Schema + 仅输出 JSON 指令；后端解析失败自动重试；仍失败进人工复核。

4. **坑 4：MQ 重复消费，同一教程被重复拆解扣费**

根因：消费者处理完服务崩溃，ACK 未发送成功，消息重新投递。

解决方案：消费幂等设计，成功后写 Redis 标记（key=task_no:tutorial_id:agent_name, TTL=7天），失败路径不留标记——键粒度与 6.2.1 一致，只到 tutorial_id 会把失败的 step 子任务堵死（见 6.2.1）。

5. **坑 5：写 MySQL 成功但 MQ 投递失败，任务永久 pending**

根因：没有投递补偿机制。

解决方案：outbox 本地消息表，写库 + 写 outbox 同事务，后台协程扫表投 MQ，兜底定时任务重投超时记录。

6. **坑 6：LLM 接口间歇性超时，无限重试打爆 API**

根因：无熔断、无限重试。

解决方案：熔断器 + 指数退避 + 最大重试次数；Agent 子任务独立失败。

7. **坑 7：批量导入几千条，任务堆积，小批量任务饿死**

根因：单队列无优先级，RabbitMQ 公平分发。

解决方案：P0/P1/P2 独立队列 + 独立消费者池，P0 有专属协程。

8. **坑 8：置信度分数忽高忽低，同一篇教程两次跑出来差 0.2**

根因：让 LLM 直接给置信度分数，不可复现。

解决方案：改成"LLM 出证据、代码算分"——LLM 只输出缺失字段、冲突对、不一致片段，代码按权重算分，结果可复现。
