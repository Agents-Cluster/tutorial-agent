## 8.1 性能设计

### 8.1.1 单条耗时模型（先算，再定目标）

单条教程的端到端耗时不等于"6 次 LLM 相加"，因为材料/工具/步骤/风险四路是**并行**的：

```
T(单条) = T(清洗) + max(T(材料), T(工具), T(步骤), T(风险)) + T(质检) + T(落库)
```

代入假设（3 000 字符中文教程，约 1.5k token 输入、各 Agent 输出 ≤ 500 token）：

| 段 | 假设 | 典型值 | 最差（重试 1 次） |
| --- | --- | --- | --- |
| 清洗 | 输出 ≈ 输入长度 | 4s | 9s |
| 四路并行 | 取最慢的一路 | 6s | 14s |
| 质检 | 输入 = 原文 + 卡片 | 5s | 12s |
| 落库 + 幂等标记 | 单事务 | 0.2s | 1s |
| **合计** | — | **≈ 15s** | **≈ 36s** |

> 「最差」指任一环节发生 1 次重试的样本，属于 P95 之外的尾部。若实测重试率 > 5%，说明 LLM 稳定性不达标——先降低重试率，再谈时延目标。

> **四路并行的前提是四路互不依赖**：材料/工具/步骤都只吃 `cleaned_text`；**风险 Agent 同样只吃 `cleaned_text`，不读 `steps_json`**。如果把步骤列表喂给风险 Agent，依赖就变成 `max(材料,工具,步骤) + 风险`，单条要多 4s，`P1` 的 16s 与 `P5` 的吞吐全部要重算（见 11.4.1 的教训：改一处依赖，四个数字失效）。代价是风险判断看不到结构化后的步骤，由质检的 `risk_suspect` 标记兜底——这是主动取舍，不是遗漏。

> 这一版的"6 个 Agent 串行 + P50 ≤ 8 秒"是拍出来的：6 次 LLM 串行最少也要 18s。改成并行编排后才有可能进 15s 以内，**因此编排器必须支持并行分支**（`errgroup.WithContext` + 四路并发），否则这条指标不成立。

### 8.1.2 吞吐模型

```
日吞吐 = 消费者数 × (有效工作时间 / 单条耗时) × 流水线利用率
       = 4 × (8h × 3600s / 15s) × 0.7 ≈ 4 × 1920 × 0.7 ≈ 5 300 条/天
```

- 4 = P0(2) + P1(1) + P2(1) 消费者（与 9.2 的 `RABBITMQ_CONSUMER_NUM_*` 一致）；
- 0.7 = 扣除排队、重试、限流等待的利用率系数；
- 单条耗时取 15s 而非 P95，避免用乐观值算吞吐；
- **成立前提：`LLM_MAX_CONCURRENT ≥ 16`**。若信号量更小，瓶颈从"消费者数"变成"信号量"，吞吐按 6.5.1 的请求秒公式重算（S=5 时约 3 050/天，P5 不成立）。

### 8.1.3 保障手段

| 手段 | 作用 |
| --- | --- |
| 四路并行编排 | 把串行 30s 压到 15s 量级，是达标前提 |
| LLM 全局信号量（默认 20） | 防止并发打爆上游；峰值并发 = 4 消费者 × 4 路 = 16，推导见 6.5.1 |
| 同步接口与异步链路隔离 | 任务提交只写库（< 50ms），绝不 await LLM |
| 卡片列表不返回 `steps_json` 全文 | 列表接口走覆盖索引，避免大字段 IO |
| 导出走异步 + 签名 URL | 大文件不占应用连接 |

## 8.2 可用性与容灾设计

### 8.2.1 故障降级矩阵

| 故障 | 影响 | 降级手段 | 用户可感知 |
| --- | --- | --- | --- |
| 单次 LLM 超时 | 该子任务失败 | 指数退避重试 3 次，仍失败转死信 | 任务进度停在某条，可单条重试 |
| LLM 整体不可用 | 流水线停摆 | 熔断 60s，任务保持 `pending` 不空转；窗口结束自动续跑（接管时序见 6.2） | 进度不动，不报错、不丢任务 |
| 某 Agent 关闭 | 卡片缺该字段 | 降置信度并强制进复核 | 卡片带 `quality_flags` |
| Redis 不可用 | 限流/锁/幂等标记失效 | 降级为"仅数据库唯一键兜底"，关闭**接口层限流计数**；锁失效时靠 `agent_items` 唯一键防重。LLM 全局信号量是进程内的，不受 Redis 影响，照旧生效（6.5.1） | 吞吐下降，正确性不破 |
| RabbitMQ 不可用 | 任务不投递 | outbox 持续积压，恢复后由兜底任务重投 | 任务延迟，不丢 |
| MySQL 不可用 | 全站不可用 | 健康检查返回 503；`restart: unless-stopped` 拉起后探活自动转 200。**API 前没有做健康摘流的 LB**：前端 nginx 只做同源转发（单 upstream、`proxy_next_upstream off`），503 原样透传给浏览器，不会自动摘除；摘除/挂回要靠外部探活（负载均衡 / uptime 监控）消费 503，没有它就只能靠人看大盘（见 9.12.3） | 503 页面 |
| MinIO 不可用 | 无法上传/下载 | 上传接口报 50301；已入库卡片仍可看 | 上传失败提示 |

**降级原则**：**宁可少字段，不可丢数据；宁可慢，不可重复扣费。**

### 8.2.2 备份与恢复

RTO / RPO 的目标值见 11.1，达成手段见 **9.9 备份与恢复**：

- MySQL：每日全量 `mysqldump` + binlog 增量，binlog 保留 7 天 → 支持按时间点恢复（PITR）；
- MinIO：教程原始文件可重放（源数据在，卡片可重建），不做实时备份；
- Redis：只存可重建数据（锁/限流/幂等标记），不做持久化承诺；
- 每季度一次恢复演练，演练记录写入 `docs/reviews/`。

> 没有 binlog 就没有分钟级 RPO。指标必须与手段对齐，否则就是把"高可用"当成形容词用。

## 8.3 可扩展性设计

| 维度 | 设计 | 前提/代价 |
| --- | --- | --- |
| 水平扩展 | 应用无状态，会话在 Redis，任务状态在 MySQL | 必须保证消费者幂等（6.2.1），否则加机器就重复扣费 |
| Agent 插件化 | 统一 `Agent` 接口（`Name`/`Run`），注册即生效 | 新 Agent 必须声明依赖的上游字段，编排器按依赖拓扑排序 |
| 场景迁移 | 换 Prompt + 换字段定义即可迁移到菜谱/科普/课程 | 需要 `card_entities.entity_type` 扩展枚举，不改表结构 |
| 存储抽象 | `Storage` 接口（MinIO / OSS 两实现） | 只换实现，不改业务代码 |
| 消息抽象 | `Publisher` / `Consumer` 接口 | 换 Redis Stream 时不影响编排逻辑 |

> 完整清单与取舍见 10.8，此处不重复。

## 8.4 可维护性设计

| 维度 | 设计 | 可验证性 |
| --- | --- | --- |
| 配置化运营 | 模型/温度/max_tokens 在 `agent_configs`，Prompt 用 `prompt_key` 指向文件版本 | 改配置不发版；启动自检兜底 |
| 可观测 | Zap（traceId 跨 MQ）+ Prometheus 指标 + Grafana 大盘 | 一条任务能从提交追到卡片 |
| 分层约束 | controller → service → repository 单向依赖 | CI 用 `go list -deps` 校验反向依赖即失败 |
| 错误码统一 | 业务码 + HTTP 语义双轨（4.5） | 前端可按 code 分支 |
| 子任务独立重试 | 失败只重跑该行 | 单条重试不触发全量重跑 |
| 文案与枚举单一来源 | 枚举在 1.1 术语表，前端从 `/api/v1/meta/enums` 拉取 | 前后端枚举不会各写一套 |

## 8.5 成本设计

降本手段的**唯一清单在 10.9.3**（含"四路合并"的 trade-off），本节不重复；成本计算式与降本系数在 **11.3**。

留给设计章的一条取舍原则：

> **只有"离线过滤"和"子任务独立重试"是无损降本**；置信度分流、缓存、关闭 Agent 都有质量代价；"四路合并成一次调用"必须有 R4 的实测数据支撑才允许启用，MVP 坚持 6 次独立调用。

## 8.6 数据质量保障手段

三层校验，逐层收窄：

| 层 | 手段 | 拦截什么 |
| --- | --- | --- |
| 导入层 | 长度阈值、编码检测、哈希去重 | 空/超短/超长/重复文本 |
| 结构层 | JSON Schema 校验 + 解析重试（5.4.1） | 字段缺失、枚举非法、JSON 破损 |
| 语义层 | 质检 Agent 出证据 + 代码算分（5.4.2） | 时序错乱、原文不一致、编造实体 |

**闭环**：低置信样本进复核 → 复核修改写入 `review_logs` → 每周导出"修改率最高的 20 条"用于 Prompt 调优 → 调优后跑同一批样本对比置信度分布变化。

> 目标值（召回率/时序正确率/解析成功率）只在 11.1 定义，验收口径见 10.6。
