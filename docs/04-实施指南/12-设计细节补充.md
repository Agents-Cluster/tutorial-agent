## 12.1 Agent 流水线的错误传播与失败隔离规则

### 12.1.1 错误传播模型

四路并行编排 (清洗 → 材料/工具/步骤/风险 → 质检) 中，不同 Agent 失败的影响**完全不同**。必须明确定义。

**清洗 Agent 失败**（整条教程标记失败）：
- 原因：下游所有 Agent 都依赖 `cleaned_text`；清洗失败意味着无法为下游提供输入
- 行为：
  - 标记 `agent_items[tutorial_id, clean] = failed`
  - 整条教程的 `agent_tasks.status` 保持 `running` 或标 `failed`（见 12.1.3）
  - 该教程不生成卡片，跳过并行四路
  - 不进人工复核（因为根本没有 output 卡片）
  - 自动重试 3 次（指数退避，见 6.3）；仍失败则进 DLX 死信

**材料/工具/步骤/风险之一失败**（该 Agent 失败，其他继续）：
- 原因：四路互不依赖，某路失败不影响其他路
- 行为：
  - 标记 `agent_items[tutorial_id, agent_name] = failed`
  - **其他三路继续执行**（使用 `errgroup.WithContext`，一路失败不 cancel 其他路）
  - 最终生成卡片时，失败路的字段为空 JSON `{}` 或 `null`
  - 该字段对应的置信度维度按"缺失"处理（见 12.2.2）
  - 卡片仍然生成，但置信度必然降低，进人工复核
  - 后续可单条重试该路（见 6.5.2）

**质检 Agent 失败**（卡片质量无法评估）：
- 原因：质检 Agent 是最后一道校验，失败意味着无法给出 `confidence_detail` 与 `quality_flags`
- 行为：
  - 标记 `agent_items[tutorial_id, quality] = failed`
  - 卡片**仍然生成**，但不计算 `confidence` 和 `confidence_detail`
  - 手动补字段：`confidence = null`, `confidence_detail = null`, `quality_flags = ["quality_agent_failed"]`
  - 强制进人工复核（review_status = `pending_review`）
  - 人工复核员可选择"手工评分" → 再提交
  - 后续可单条重试质检 Agent

### 12.1.2 并行分支的实现约束

为了保证四路真正并行，必须满足以下约束：

| 项 | 要求 | 原因 |
|---|------|------|
| 材料 Agent 输入 | 仅 `cleaned_text` | 不能读 `tools`/`steps`/`risk` 的输出 |
| 工具 Agent 输入 | 仅 `cleaned_text` | 同上 |
| 步骤 Agent 输入 | 仅 `cleaned_text` | 同上 |
| 风险 Agent 输入 | 仅 `cleaned_text`，**不读 `steps_json`** | 8.1.1 已说明，读 steps 则吞吐要重算 |
| 质检 Agent 输入 | 原文 + 卡片 JSON（上四路聚合后的结果） | 质检是最后一步，依赖前序结果 |

**实现检查清单** (代码审查时必须验证)：
```go
// orchestrator.go 中，材料/工具/步骤/风险的 run 函数不能访问彼此的结果
// 正确做法：
err := eg.WithContext(ctx).Go(func() error {
    return m.runMaterialAgent(ctx, cleanedText)  // 仅传 cleanedText
})
err := eg.WithContext(ctx).Go(func() error {
    return m.runToolAgent(ctx, cleanedText)      // 仅传 cleanedText
})
// ...

// 错误做法（会导致吞吐计算失效）：
err := eg.WithContext(ctx).Go(func() error {
    return m.runRiskAgent(ctx, cleanedText, stepsResult)  // ❌ 不能等 stepsResult
})
```

### 12.1.3 任务级失败判定规则

一个任务（多条教程的批次）什么时候标记为 `failed`？

| 触发条件 | 任务状态 | 处理 |
|---------|--------|------|
| 所有子任务都成功 | `succeeded` | 进度 100%，关闭 |
| ≥1 条教程生成了卡片（即使置信度低） | `succeeded` | 任务完成，低置信的卡片进复核 |
| 全部子任务失败（无一条卡片）| `failed` | 标记错误原因，可整体重试 |
| 清洗 Agent 全局不可用（熔断 60s）| `pending` | 不标 failed，等候熔断解除 |
| 单条子任务进死信（重试超限）| `succeeded`（任务不因子任务死信而失败） | 该条教程标记丢弃，统计到 `dead_items` |

**关键决策**：任务成功的定义是"至少产出一条卡片"，不是"全部成功"。低置信卡片由人工复核承载。

## 12.2 置信度计算的完整规则

### 12.2.1 四维置信度的公式与权重

**定义**：置信度是"该卡片有多可信"的 0-1 浮点数。由四个维度加权计算。

**公式**：
```
confidence = 0.30 × completeness + 0.30 × temporal + 0.20 × grounding + 0.20 × quality
```

**权重说明**：
- `completeness` (30%)：卡片字段完整度。最直观的衡量
- `temporal` (30%)：步骤时序正确度。步骤错乱是最严重的错误
- `grounding` (20%)：实体与原文的对应度。evidence 匹配率
- `quality` (20%)：其他综合质量指标。包括清洗质量、句子可读性等

### 12.2.2 各维度的具体计算方法

#### **Completeness（字段完整度）**

基线值：1.0

扣分规则（扣分**叠加**，不求平均）：

| 缺失情况 | 扣分 | 说明 |
|---------|------|------|
| 材料为空 | -0.10 | `materials === null` 或 `[]` |
| 工具为空 | -0.10 | `tools === null` 或 `[]` |
| 步骤为空 | -0.15 | `steps === null` 或 `[]; 步骤是最核心字段` |
| 风险为空 | -0.05 | `risks === null` 或 `[]; 可选信息` |
| 某材料缺 spec | -0.03/个 | 单条材料 `spec === null` |
| 某步骤缺 action | -0.05/个 | 单条步骤 `action === null \|\| ""` |

**计算示例**：
```
基线 = 1.0
- 材料为空: -0.10
- 步骤缺 2 个 action: -0.10
结果 = max(0, 1.0 - 0.10 - 0.10) = 0.80
```

**下界**：`completeness ≥ 0`（即使全缺也是 0，不能负数）

#### **Temporal（步骤时序正确度）**

基线值：1.0

输入：质检 Agent 输出的 `step_conflicts[]` 数组（每项是 `{step_a_seq, step_b_seq, reason}`，表示第 a 步和第 b 步顺序有冲突）

**计算**：
```
冲突对数 = len(step_conflicts)
总步骤数 = len(steps)

如果 总步骤数 ≤ 1 → temporal = 1.0（无法时序冲突）
否则 → temporal = max(0, 1.0 - 0.15 × 冲突对数 / 总步骤数)
```

**示例**：
```
5 步中发现 2 个冲突对
temporal = 1.0 - 0.15 × (2/5) = 1.0 - 0.06 = 0.94
```

**下界**：`temporal ≥ 0`

#### **Grounding（实体与原文对应度）**

基线值：1.0

输入：所有实体（材料、工具、步骤）中带有 `evidence` 字段的，逐条检查是否在 `raw_text` 中命中

**计算**：
```
总实体数 = len(materials) + len(tools) + len(steps)
有效实体数 = 有 evidence 字段的实体数（步骤的 evidence 从 action 推导）
命中数 = evidence 在 raw_text 中能找到的实体数（子串匹配，case-insensitive）

如果 总实体数 === 0 → grounding = 1.0
否则 → grounding = 命中数 / 有效实体数
```

**示例**：
```
5 个材料 + 3 个工具 + 8 个步骤 = 16 个实体
其中 15 个有 evidence，1 个缺失
命中 14 个
grounding = 14 / 15 = 0.933
```

**补充**：若实体是 Agent 失败时的空结果（材料为 `null`），该维度对应的实体数记为 0，不参与分母：
```
// 假设材料 Agent 失败，材料为 null
有效实体数 = 0（材料） + 3（工具） + 8（步骤） = 11
```

#### **Quality（综合质量指标）**

基线值：1.0

综合多个子指标，扣分**叠加**：

| 指标 | 触发条件 | 扣分 |
|-----|---------|------|
| 清洗质量差 | `clean_degraded` flag（见 5.1.5） | -0.10 |
| 高风险未标记 | `risk_suspect` flag（步骤含高温/明火但 risks 为空） | -0.05 |
| 步骤可读性差 | 步骤 action 平均长度 < 10 字符（碎片化）| -0.05 |
| 材料用量不合理 | 某材料 qty > 100 或 < 0.01（极端值） | -0.03/个 |

**计算示例**：
```
基线 = 1.0
- 清洗降级: -0.10
- 高风险未标: -0.05
结果 = max(0, 1.0 - 0.10 - 0.05) = 0.85
```

### 12.2.3 总置信度的最终规则

```
confidence = 0.30 × completeness + 0.30 × temporal + 0.20 × grounding + 0.20 × quality
```

**分流阈值**（见 11.1）：
- `confidence ≥ 0.80` → `auto_passed`，直接入库
- `0.50 ≤ confidence < 0.80` → `pending_review`，进人工复核
- `confidence < 0.50` → 标记 `low_confidence` flag，人工复核时置顶优先

**异常情况**：
- 质检 Agent 失败 → `confidence = null`, 强制进复核
- 4 个维度中≥2 个为 `null`（多路 Agent 失败） → `confidence = null`, 强制进复核

## 12.3 卡片生命周期与访问控制规则

### 12.3.1 卡片状态转移矩阵（完整版）

| 当前状态 | 可转移到 | 操作者 | 触发条件 | 接口 |
|--------|--------|------|--------|------|
| `draft` | `published` | editor | 人工审核通过，决定发布 | `PUT /cards/{id}/publish` |
| `draft` | `archived` | editor | 决定隐藏或淘汰 | `PUT /cards/{id}/archive` |
| `published` | `archived` | editor | 下架已发布内容 | `PUT /cards/{id}/archive` |
| `archived` | `published` | admin | 恢复已下架内容 | `PUT /cards/{id}/unarchive` |
| `archived` | `draft` | 不允许 | — | — |
| `published` | `draft` | 不允许 | — | — |

**关键决策**：
- 反向转移（如 `published` → `draft`）不允许，保证内容流向单向
- 只有 `admin` 才能从 `archived` 恢复到 `published`，编辑只能下架不能恢复

### 12.3.2 卡片可见性规则

| 用户角色 | 可见范围 | 可编辑范围 | 可导出 |
|---------|--------|----------|------|
| `viewer` | `published` 状态，且 license 非 `research-only` | 不可编辑 | 不可导出 |
| `editor` | 自己导入的教程集下的所有卡片（draft/published/archived） | `draft` → 编辑内容；`published` 无法编辑只读 | 仅 `published` 的可导出 |
| `admin` | 全部卡片（所有教程集、所有状态） | 全部可编辑（含复核和发布决策） | 全部可导出（含 `draft`） |

**接口行为**：
```go
// GET /cards (列表)
// - viewer: 返回 published 且非 research-only 的卡片
// - editor: 返回自己集下的所有卡片
// - admin: 返回所有卡片

// GET /cards/{id} (详情)
// - 若卡片 license=research-only 且用户是 viewer → 返回 403 Forbidden
// - 若卡片不是自己集下的且用户是 editor → 返回 403

// PUT /cards/{id} (编辑)
// - 仅 draft 状态允许编辑
// - editor 仅能编辑自己集下的卡片
// - 编辑完自动重置 review_status=auto_passed, 置信度重新计算吗？（见 12.3.3）

// PUT /cards/{id}/publish (发布)
// - editor 可发起，但需要... 自动发布还是需要 admin 审批？（见 12.3.3）
```

### 12.3.3 编辑与发布的流程选择

**当前设计中有歧义**：编辑一张 draft 卡片后，是否自动发布？还是需要人工审批？

**两种选择方案**（从项目背景 1.3 的"用置信度分流 + 人工复核"来看，应选 B）：

**方案 A（自动发布）** —— 简单但不符合"人工复核"的承诺
```
1. Agent 生成卡片 → draft + auto_passed
2. Editor 编辑卡片（改措辞、改字段值）
3. 编辑完点"发布" → 自动变 published + 卡片立即对外可见
缺陷：绕过了"人工复核"，后续数据质量无保证
```

**方案 B（需人工发布决策）** ✅ 推荐
```
1. Agent 生成卡片 → draft + auto_passed（高置信）或 draft + pending_review（低置信）
2. Editor 可选择：
   a. 低置信卡片 → 打开复核页面编辑 → 保存 → 仍是 draft + pending_review
   b. 高置信卡片 → 可直接"发布" → published
   c. 任何卡片 → 编辑后的保存 → 重新计算置信度，若降低则进复核
3. Admin（或 reviewer role） 在"待复核队列"里审查低置信卡片
   → 通过 → 发布（published）
   → 拒绝 → 标记 rejected，Editor 可重新编辑或丢弃
```

**建议采用方案 B**（与项目定位一致），并补充接口定义：

| 接口 | 调用者 | 作用 |
|-----|-------|------|
| `PUT /cards/{id}` | editor | 编辑 draft 卡片，保存后置信度重算，若 < 0.80 则进复核 |
| `PUT /cards/{id}/publish` | editor（仅高置信） + admin（任何置信度） | 发布卡片到 published |
| `PUT /cards/{id}/archive` | editor + admin | 下架卡片 |
| `PUT /cards/{id}/review` | admin/reviewer | 对 pending_review 卡片进行人工审查，输入修改建议和最终决策 |

## 12.4 许可证合规过滤规则

### 12.4.1 许可证值的完整定义

`tutorial_sets.license` 的**全部取值**（不在此列视为非法）：

| 许可证代码 | 含义 | 能否商用 | 能否导出 | 约束 |
|-----------|------|--------|--------|------|
| `cc-by-nc-sa-4.0` | CC-BY-NC-SA 4.0 | ❌ 否 | ✅ 可（非商用） | 必须署名、不能商用、衍生物同协议 |
| `cc-by-sa-4.0` | CC-BY-SA 4.0 | ✅ 是 | ✅ 可 | 必须署名、衍生物同协议 |
| `cc-by-4.0` | CC-BY 4.0 | ✅ 是 | ✅ 可 | 必须署名 |
| `public-domain` | 公有领域 | ✅ 是 | ✅ 可 | 无约束 |
| `research-only` | 研究专用 | ❌ 否 | ✅ 可（研究用途） | 不能商用、平台专用 |
| `self-owned` | 自有内容 | ✅ 是 | ✅ 可 | 无约束 |
| `proprietary` | 专有 | ❌ 否 | ❌ 不可 | 仅平台内部使用，不能导出 |

### 12.4.2 导出合规过滤规则

**规则**：导出时按 `tutorial_sets.license` 过滤，只导出符合申请用途的教程集

**4.3.7 的合规过滤（SQL）**：

```sql

-- 系统按 use_case 过滤教程集

-- commercial 用途 → 仅允许导出 CC-BY / CC-BY-SA / public-domain / self-owned
SELECT * FROM tutorial_sets 
WHERE license IN ('cc-by-4.0', 'cc-by-sa-4.0', 'public-domain', 'self-owned')

-- research 用途 → 允许 research-only 及上述全部
SELECT * FROM tutorial_sets 
WHERE license IN ('cc-by-nc-sa-4.0', 'cc-by-4.0', 'cc-by-sa-4.0', 
                   'public-domain', 'self-owned', 'research-only')

-- internal 用途 → 全部可导出

```

```
export_task 记录 use_case，后续生成文件前再校验一次
```

## 12.6 Quality Agent 的准确率保证与补偿

### 12.6.1 质检 Agent 的 SLA 定义

质检 Agent 是 LLM 调用中最关键的一环，因为代码算分完全依赖它的输出。其准确率直接影响整个置信度系统的可信度。

**SLA 指标**（在 `internal/observability/metrics.go` 中埋点）：

```go
// 质检 Agent 的三个关键指标
metricQCMissPairRate    // 质检漏掉的步骤冲突对比例 (recall 反面)
metricQCFalsePairRate   // 质检误判的步骤冲突对比例 (precision 反面)
metricQCGroundingRecall // 质检捕获的 grounding 问题的 recall
```

**目标值**（见 11.1）：
- `QC_STEP_CONFLICT_RECALL ≥ 0.90`：漏掉真实冲突对的概率 ≤ 10%
- `QC_GROUNDING_RECALL ≥ 0.85`：漏掉真实 grounding 问题的概率 ≤ 15%

### 12.6.2 质检漏判的检测与补偿

**问题**：质检 Agent 输出的冲突对数无法完全正确。若漏判，代码算出的 `temporal` 维度就虚高。

**检测机制**：人工复核员可在复核页面进行"二次质检"。

```go
// 复核页面允许：
type ReviewAction struct {
    CardID    uint64
    Decision  string // approved / rejected / escalate
    Changes   *CardChanges
    AdditionalIssues []QCIssue // 复核员发现的额外问题（质检漏掉的）
}

// AdditionalIssues 作为"质检漏判"的信号被上报
// 后续用来：1) 改进 Prompt；2) 调整模型选择；3) 评估质检准确率的实际值
```

**补偿手段**：

1. **定期审计**（月度）：随机抽检 100 张已发布卡片的复核员复查
   - 记录复核员发现的额外问题数
   - 计算质检 Agent 的实际 recall = (冲突对总数 - 漏判数) / 冲突对总数
   - 若实际 recall < 0.85，启动 Prompt 优化

2. **触发式审查**（实时）：
   - 若某条教程的复核员修改数 > 3，标记为"质检可能欠佳"
   - 过 24h 后选 5 条类似教程，重跑质检 Agent 看是否是系统性问题

3. **模型切换预案**：
   - 若 DeepSeek 的质检准确率不达标，切 GPT-4 或豆包重跑
   - 结果对比并决定是否长期切换

### 12.6.3 质检 Agent 失败的处理

见 12.1.1，质检 Agent 失败时的行为定义。

## 12.7 Dev vs Prod 部署的差异与 LB 联动

### 12.7.1 部署环境的清晰区分

| 维度 | Dev（docker-compose） | Prod（K8s / VM） |
|-----|-------|------|
| 组件 | Go app / MySQL / Redis / RabbitMQ / MinIO，同宿主 | 分布式部署，可跨机房 |
| 健康检查 | `/health` 接口，compose restart 自行判断 | `/health` 接口，外部 SLB 主动探活 |
| 摘流 | 不支持。503 原样返回浏览器 | SLB 主动摘除，自动转移流量 |
| 故障恢复 | 手工 docker-compose up / 或自动 restart: unless-stopped | SLB + HPA 自动恢复 |
| 监控 | 本地日志，可选接 Prometheus | 必须接 Prometheus / DataDog |
| 备份 | 可选（开发环境） | 必须，RTO ≤ 1h（见 11.1）|

### 12.7.2 健康检查接口的完整设计

```go
// GET /health
// 返回系统各组件的状态

type HealthResponse struct {
    Status    string                     // "healthy" / "degraded" / "unhealthy"
    Timestamp time.Time
    Components map[string]ComponentHealth
}

type ComponentHealth struct {
    Status  string // "up" / "down" / "slow"
    Latency int    // ms
    Detail  string
}

// 返回示例
{
    "status": "healthy",
    "timestamp": "2026-10-19T10:30:00Z",
    "components": {
        "mysql": {"status": "up", "latency": 2},
        "redis": {"status": "up", "latency": 1},
        "rabbitmq": {"status": "up", "latency": 5},
        "minio": {"status": "up", "latency": 50},
        "llm_api": {"status": "slow", "latency": 3000, "detail": "DeepSeek 响应缓慢"}
    }
}

// 状态规则
if mysql.down || redis.down → 503 unhealthy
if llm_api.down → 200 degraded（任务继续排队，不影响数据读取）
if minio.down → 200 degraded（已有卡片可读，上传失败）
```

**SLB 配置**：
```
Health check path: /health
Success codes: 200
Failure codes: 500, 503
Interval: 10s
Timeout: 3s
Unhealthy threshold: 3 consecutive failures → 摘除实例
Healthy threshold: 2 consecutive successes → 挂回实例
```

### 12.7.3 Prod 环境的 LB 配置示例

```nginx

    server app-1:8080;

    }
}
```

## 12.8 Prompt Override 的使用规则

### 12.8.1 `agent_configs.prompt_override` 的设计目的

运营级 Prompt 覆盖用于**快速 A/B 测试或紧急修复**，不走代码发版流程。

| 场景 | 使用 override | 不使用 override |
|-----|-------------|--------------|
| 修复 Prompt 的明显 bug（如写错了物品单位） | ✅ 使用 | ❌ 不用 |
| 尝试新的 Prompt 版本 A/B 测试 | ✅ 使用 | ❌ 不用 |
| 改变 Prompt 的整体策略 | ❌ 不用 | ✅ 走代码发版 |

### 12.8.2 Override 的生效规则

```go
// internal/ai/prompts.go

func GetPromptForAgent(agentName string) string {
    // 1. 查询 agent_configs 表
    config := db.GetAgentConfig(agentName)
    
    // 2. 优先级：override > 内置版本
    if config.PromptOverride != nil && config.PromptOverride != "" {
        return config.PromptOverride  // 使用运营覆盖
    }
    
    // 3. 否则使用内置版本
    promptKey := config.PromptKey // e.g., "builtin:clean@v1"
    builtinPrompt := LoadBuiltinPrompt(promptKey)
    return builtinPrompt
}
```

**生效时机**：
- 更新 `prompt_override` 后，下一条新任务生效（不影响进行中的任务）
- 不需要重启应用

**回滚方法**：
- 将 `prompt_override` 设为空字符串或 NULL，即恢复内置版本

### 12.8.3 运营界面（Admin 页面）

```
Agent 配置 → [material_agent]
┌─────────────────────────────────────┐
│ 内置版本: builtin:material@v1       │
│                                     │
│ [显示内置 Prompt] (只读)             │
│                                     │
│ 运营覆盖:                            │
│ ┌───────────────────────────────┐  │
│ │ (输入框，可粘贴新 Prompt)      │  │
│ └───────────────────────────────┘  │
│                                     │
│ [预览] [保存] [重置为内置版本]      │
└─────────────────────────────────────┘
```

**权限**：仅 admin 可修改。

## 12.9 软删除与恢复的隔离期与策略

### 12.9.1 删除后的恢复可能性

| 删除对象 | 物理删除 | 软删除 | 恢复隔离期 | 恢复方式 |
|--------|--------|------|----------|--------|
| 教程集 | ❌ | ✅ | 7 天 | admin 手工恢复（解除 deleted_at） |
| 教程 | ❌（级联隐藏） | ✅ | 随教程集 | 恢复教程集即自动恢复 |
| 卡片 | ❌（级联隐藏） | ✅ | 随教程集 | 同上 |
| 导出任务（过期） | ✅ | 无 | 24h | 不可恢复，用户需重新导出 |
| 操作审计日志 | ✅ | 无 | 按法规要求（默认 2 年） | 不可恢复，归档查询 |

### 12.9.2 恢复流程

```go
// PATCH /tutorial-sets/{id}/restore
// 仅 admin 可调用，且教程集必须是 deleted_at IS NOT NULL 的状态

type RestoreRequest struct {
    ConfirmFlag bool // 必须显式确认
}

// 恢复逻辑
func RestoreTutorialSet(id uint64) error {
    // 1. 检查是否在隔离期内（删除 ≤ 7 天）
    set := db.GetTutorialSet(id)
    if time.Since(set.DeletedAt) > 7*24*time.Hour {
        return errors.New("隔离期已过，无法恢复")
    }
    
    // 2. 解除 deleted_at
    db.Model(&set).Update("deleted_at", nil)
    
    // 3. 级联恢复下属 tutorials 和 cards（set deleted_at = NULL where set_id = id）
    db.Model(&Tutorial{}).Where("set_id = ?", id).Update("deleted_at", nil)
    db.Model(&Card{}).Where("tutorial_id IN (SELECT id FROM tutorials WHERE set_id = ?)", id).
        Update("deleted_at", nil)
    
    // 4. 记录操作审计
    LogOperation(userID, "tutorial_set:restore", "tutorial_set", id)
    
    return nil
}
```

**UI 交互**：
```
教程集列表 → [已删除] 标签 → 点击进入详情 → "此集已删除，7 天内可恢复"
→ [恢复] 按钮 → 弹框确认 → 执行恢复
```

## 12.10 卡片编辑后的置信度重算

### 12.10.1 编辑触发的置信度重新评估

当编辑器修改一张卡片时（`PUT /cards/{id}`），置信度需要重新计算。但**不重新调用质检 Agent**（为了避免额外成本）。

**规则**：
1. 编辑保存 → 触发置信度重算（调用 scorer.go）
2. 新置信度 < 旧置信度 → 卡片自动从 `published` 降回 `draft` + `pending_review`
3. 新置信度 ≥ 旧置信度 → 卡片保持原状态

**代码实现**：

```go
// PUT /cards/{id}
func UpdateCard(cardID uint64, changes *CardChanges) error {
    // 1. 查询旧卡片
    oldCard := db.GetCard(cardID)
    oldConfidence := oldCard.Confidence
    
    // 2. 应用变更
    newCard := oldCard.Clone()
    newCard.ApplyChanges(changes)
    
    // 3. 重算置信度（不调用质检 Agent）
    // 假设 qcEvidence 从数据库读取（存在 cards.removed_spans 等）
    newConfidenceDetail := scorer.ScoreConfidence(newCard)
    newConfidence := newConfidenceDetail.ToTotal()
    
    // 4. 检查置信度变化
    if newConfidence < oldConfidence {
        // 置信度下降 → 强制进复核
        newCard.ReviewStatus = "pending_review"
        if newCard.Status == "published" {
            newCard.Status = "draft" // 从 published 降回 draft
        }
    }
    
    // 5. 保存
    db.Save(newCard)
    
    return nil
}
```

### 12.10.2 哪些编辑会改变置信度

| 编辑操作 | 影响维度 | 置信度变化预期 |
|---------|--------|------------|
| 修改材料名称 | grounding | ↓（evidence 需重新匹配） |
| 删除一个步骤 | temporal | ↑（步骤少，冲突对也少） |
| 修改风险描述 | quality | ↓（清洁度降低） |
| 修改步骤 uses 关联 | grounding | 可能↓（关联错误） |
| 修改 evidence 链接 | grounding | ↓ |

**编辑时的提示**：
```
[保存] 按钮下显示警告
"修改后置信度可能下降。保存后将重新评估。"
```
