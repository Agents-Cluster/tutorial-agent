# Baseline 对照实验设计

> 回答"你说多 Agent 更好，有数据证明吗"。
> 本文件定义**实验协议**；实验结果的唯一登记处是 11.2 的 R1–R4 行，本文不写结论数字。

---

## B.1 实验目的

在同一批样本、同一模型、同一温度下，比较两种抽取方式的差异：

- **A 组（单轮 baseline）**：一次 Prompt，要求输出完整卡片 JSON；
- **B 组（多 Agent）**：清洗 → 材料/工具/步骤/风险（并行）→ 质检。

要回答三个问题：召回率高多少、JSON 稳定性好多少、代价（token / 时延）是多少倍。

## B.2 实验设计

| 项 | A 组（单轮） | B 组（多 Agent） |
| --- | --- | --- |
| 样本集 | 200 条中文标注集 v1（高质量/中噪声/低质各 1/3） | 同左，**逐条同一份原文** |
| 调用次数 | 1 次/条 | 6 次/条（并行编排） |
| 模型 / 温度 | 同一模型，`temperature=0.1` | 同一模型；清洗/材料/工具/步骤/风险 `0.1`，质检 `0.0` |
| 输出约束 | 同一份 Card Schema（5.2） | 同左 |
| 重试 | 解析失败重试 1 次 | 同左 |
| 判定人 | 标注员 A + B 独立判定，不一致由 C 仲裁 | 同左 |
| 标注一致性 | Cohen's Kappa ≥ 0.75 才可用于结论 | 同左 |
| 运行环境 | 同一 API Key、同一时段、串行执行避免限流干扰 | 同左 |

**公平性约束**（缺一条结论就不可信）：

1. 两组的 **Prompt 里都包含完整的 Card Schema 和字段枚举**，只有"是否拆分任务"这一个变量不同；
2. 两组的**样本顺序相同**，且都无缓存（每组跑前清 `LLM` 结果缓存）；
3. 判定人对"哪组是机器产出"不知情（盲评）；
4. 失败样本**计入分母**，不允许剔除——否则 JSON 解析失败率高的一组反而占便宜。

## B.5 判读规则（先定规则，再看结果）

| B 组相对 A 组 | 结论 | 后续动作 |
| --- | --- | --- |
| 召回 +≥10pp 且 token ≤ 6 倍 | 多 Agent 成立，可写进 README | 继续调 Prompt 提质 |
| 召回 +5~10pp | 部分成立，需说明边际收益 | 在 README 写"提升有限，代价 5×" |
| 召回 +<5pp | 不成立 | 回到流水线设计，别写"多 Agent 更好" |
| 召回提升但 JSON 成功率下降 | 实现有问题（多半是并行编排串了上下文） | 先修，不发布结论 |

> 这条规则的意义：**先承诺"什么结果算失败"**，避免看到数据后自我解释。

## B.6 复现步骤

```bash
# 1) 固定样本与版本
python scripts/preprocess.py --input data/raw --out data/eval_v1 --seed 42

# 2) A 组（单轮）
go run ./cmd/bench -mode=single -set=data/eval_v1 -model=$LLM_MODEL -temp=0.1 -out=out/a.jsonl

# 3) B 组（多 Agent，同一份原文、同一顺序）
go run ./cmd/bench -mode=pipeline -set=data/eval_v1 -model=$LLM_MODEL -temp=0.1 -out=out/b.jsonl

# 4) 出对比报告（差异明细 + 指标汇总，写入 11.2 待填行）
go run ./cmd/bench -mode=report -a=out/a.jsonl -b=out/b.jsonl -gold=data/eval_v1/labels.jsonl
```

> `cmd/bench` 是离线跑批工具，不依赖 MySQL/MQ，只依赖 LLM API——保证实验可复现、不被环境干扰。
